# Team model 4: each team names the souls that may join it

**Status:** the shape is agreed by both maintainers' sides. Not implemented. Implementation waits for
the two items under [Open](#open). When it ships, this record supersedes the `souls:` and shared-team
syntax of [team model 3](2026-10-02-team-model-3.md). Model 3's reasons, its closed-by-default local
teams and its limits (what it protects against, and what it does not) stand.

## The shape

```yaml
defaultTeam: engineering            # the fallback, for a soul no souls: entry matches

souls:
  ops/reviewer:
    defaultTeam: engineering

teams:
  engineering:
    teamId: "engineering:acme.example"
    eligibleForSouls: [ops/*]
  security:
    teamId: "security:acme.example"
    eligibleForSouls: [ops/reviewer]
```

| Model 3 | Model 4 |
|---|---|
| `teams.<label>.team` | `teams.<label>.teamId` |
| `souls.<pattern>.default` | `souls.<pattern>.defaultTeam` |
| `souls.<pattern>.teams: [labels]` | the pattern, in each team's `eligibleForSouls` |
| `souls.<pattern>.teams: any` | removed; the pattern, in each team's `eligibleForSouls` |

`teams.<label>.description`, the workspace `defaultTeam` and `localTeams` are unchanged.

## Rules

1. **Patterns** are today's: `<member|package>/<soul>`, `<member|package>/*` and `"*"`. A bare `*` in
   `eligibleForSouls` means every soul (quoted in YAML).
2. **Eligibility is a union.** A soul may join a team when any pattern in that team's
   `eligibleForSouls` matches it. There are no exclusions. A shared team with no `eligibleForSouls`,
   or an empty one, offers itself to no soul.
3. **A soul's default** comes from the most specific `souls:` entry that matches it. An entry holds
   `defaultTeam` and nothing else, and it is required.
4. **A `souls:` default must be eligible.** Every `souls.<pattern>.defaultTeam` names a shared team
   of this file whose `eligibleForSouls` has that pattern or a broader one. Otherwise the file is
   refused: `E_WORKSPACE_SCHEMA`, naming the pattern and the team. The check compares patterns, so it
   needs no discovery: `ops/*` is covered by `ops/*` or `*`, and not by a list of `ops/<soul>` entries.
5. **Without a matching entry** the order is model 3's: the deployment's local `defaultTeam` where
   local teams are allowed, then the workspace `defaultTeam`, then none.
6. **Local teams** in `oats-local.yaml` take the same keys (`teamId`, `eligibleForSouls`), with one
   spelling in both files. `localTeams` decides whether they are allowed, as today.
7. A label never gates or changes trust. `team-soul-unknown` also checks the patterns in
   `eligibleForSouls`, and `"*"` never raises it.

## What changes for a workspace

**Narrowing.** In model 3 the most specific `souls:` entry gives a soul's teams outright, so
`"*": {teams: [general]}` with `ops/ci: {teams: []}` keeps `ops/ci` out of `general`. Model 4 cannot say
"every soul but this one". The owner lists the souls that may join instead.

**A printed rewrite must not widen eligibility.** Converting a model 3 file must evaluate the old
rules for each discovered soul, and list patterns only where every soul they match was eligible.
Where the souls cannot all be read, it prints no rewrite for the affected entries and says why.
`any` includes the teams in the file at conversion, not teams added later.

## Readers, all in one release

- **Kernel:** both schemas, the workspace validation (`lib/workspace.mjs`), `lib/teams.mjs`, and the
  verbs (`lib/teams-verbs.mjs`): `oats teams add` writes `teamId`.
- **JSON:** `oats teams --json` and `oats soul teams --json` change shape (`souls` and `match`), so
  their API numbers and the kernel feature move. Resolved team rows keep `{ label, team, default, from,
  via }`, as do `OATS_TEAMS` and `instance.json`: a running home and a provider hook see no change.
- **Readiness and doctor:** messages and fixes name the new keys.
- **Desktop:** the team views and their fixtures, recorded from the kernel that ships.
- **Teaching:** `oats.setup` (`/oats-teams`, `/oats-workspace-config`, `/oats-setup-model`,
  onboarding), and the workspace, configuration, first-team, capabilities and Desktop API pages.
- **oats-aweb:** it prints `teams:` and `souls:` snippets for the operator to commit. They must match
  the kernel it runs under, so its change is released with the kernel's.

## Acceptance

Each test fails before the change.

1. The shape above resolves: `ops/reviewer` defaults to `engineering` and may join `security`; another
   `ops/` soul, with no entry, gets the workspace default and may join `engineering`, not `security`.
2. Two patterns in two teams give a soul both teams; the most specific `souls:` entry gives its default.
3. A `souls:` default whose team doesn't cover the pattern is refused, naming both; `*` covers all.
4. `eligibleForSouls: ["*"]` admits member, package and external souls; absent or `[]` admits none.
5. `teams: any` is refused, and an unknown key in a team or a `souls:` entry is refused.
6. A narrowing model 3 file (above) never gets a rewrite that admits the narrowed soul.
7. `OATS_TEAMS`, `OATS_DEFAULT_TEAM*` and the recorded rows are byte-for-byte what the equivalent
   model 3 file gives.
8. The Desktop reads documents recorded from the real kernel, not written by hand.

## Open

1. **The old keys** (`teams.<label>.team`, `souls.<pattern>.default` and `.teams`): read for a
   deprecation period, or refused with the rewrite printed. Not decided. No compatibility code is
   written before it is. If they are read, the decision also covers a file that mixes both forms.
2. **A local team without `eligibleForSouls`.** Today every soul may join every local team. Proposed:
   absent means none, as for a shared team, and `oats teams add` writes `eligibleForSouls: ["*"]`, so
   one key has one meaning in both files.

## Out of scope

Exclusion patterns, per-team roles, enforcement in the messaging layer, and any change to how a home
joins or leaves a team.
