# OATS 0.69.24

Unreleased

The kernel can run an agent on a session backend a capability supplies, beside
tmux (session providers, experimental until the follow-up change). The Desktop
shows an agent's board around its terminal: its facts, and its questions
answered by number. OATS now refuses to start on Node.js older than 22.
oats.framework 1.28.0 and oats.aweb 1.47.0 are pinned.

## Upgrade

- **The catalog pins oats.framework 1.28.0 and oats.aweb 1.47.0**; oats.okf
  stays 6.3.0. `oats sync` takes them. Existing homes take oats.core 2.16.0
  (the `tui` default) through `oats instance upgrade` or a respawn.
- **A legacy oats.aweb grant seat** (one spawned with oats.aweb 1.12–1.24)
  fills its `.oats-aweb/seat.json` once at its next start, from facts that
  must agree; otherwise its start refuses with the respawn remedy. Such a
  seat no longer follows a changed default team: respawn it to move it.

- **What users must do: move to Node.js 22.5 or later.** OATS now stops before
  every command on Node below 22, including `version`, the reader and
  capability commands. If you run OATS on Node 20 today, upgrade Node before continuing.
  Node 18 and 20 receive `E_NODE_UNSUPPORTED` with exit 1, as one failure
  envelope on stdout with `--json`, or a message on stderr without it. Remote
  probes and Desktop discovery retain the host's refusal message. The npm
  package retains its Node 22.5.0 floor so installation warns about it.

- **Respawn an instance of `oats-maintainer` or `oats-setup-admin` once**
  after `oats sync`. An instance keeps the `okf.json` its spawn recorded, so
  one started before this release still reads and proposes to its old node; a
  new spawn reads the soul's subjects. The soul needs a knowledge base bound
  with the subject layout: on a base that is not bridged, its spawn refuses
  with `E_CONFIG` naming the base
  ([okf.json version 2](../knowledge.md#the-souls-okfjson)).

## Added

- **Doctor reports Git's cache support.** Text and JSON doctor output name
  the Git version and whether it supports partial caches or uses the
  whole-tree fallback. This uses the existing `information[]` field, adds no
  warning and refuses nothing. Git 2.45 or later is recommended for partial
  caches; an older Git works with whole-tree fetches.

- **The Desktop and the TUI show an agent that runs on a session provider
  as OATS reports it.** A session provider is a session backend a capability
  supplies, in place of tmux; this release's kernel reports them (session
  providers, below), and no released provider exists yet. For such an agent:
  - its state is the one OATS reports, and no client asks tmux about it;
  - Start, Restart, Stop and Retire are offered by its state, as for any
    agent;
  - it shows as needing input whenever OATS reports that it waits on you
    and it is not stopped, and the Desktop's Home lists it under Running
    while it runs;
  - there is no terminal to open. The clients say where it runs ("Runs in a
    bb thread; open it in bb.") and show the link the provider offers: the
    Desktop in the row's context menu, opened in your browser, and the TUI
    printed under the line after `Enter`. Neither opens, splits or restores
    a terminal tab for it;
  - the row's tooltip in the Desktop names the backend and the provider's
    thread id.

  An agent in tmux, and one recorded on Herdr, read as before
  ([how the clients read `backend`](../desktop-cli-api.md#row-backend-clients)).

- **The agent view in the Desktop.** With an OATS that reports the agent's board (feature `instance-board`), an agent's terminal tab shows what the agent keeps in your view and what it asks you:
  - **Facts** above the terminal: `label · value unit`, "updated <time>", at most three shown and the rest folded, a sparkline once the view has read the history, and links shown as attributed text: a press shows the whole address, and Open in browser opens it. In a short pane the facts give way so the terminal keeps its room. × or u hides a fact on this computer only, until its value changes.
  - **Questions** under the terminal, one at a time, with "question n of N", ‹ › and the dots, and a context fold (c opens it from the keyboard).
  - **Answering:** The questions and the facts are F6 regions (Ctrl+Shift+F6 from the terminal reaches the questions), and the palette's Agent: questions and facts (focus) moves through them; no chord takes Alt+T, Claude Code's extended thinking. A number puts `<id>: <option>` on the agent's input line, unsent, and your Enter in the terminal sends it. No bare digit is ever typed, and nothing is typed into a terminal that isn't on screen, or into one in its scrollback or one it can't check. A question's card stays until the agent clears it. On an agent on another machine the numbers are disabled and the zone says to type the answer in its terminal. While the agent's terminal shows a harness prompt (a live `permission` or `question` claim), the numbers are disabled and the zone says to answer the prompt there first.

  Without the feature the terminal tab and its waiting row are as before.

- **Session providers: a capability can supply a session backend** (feature
  `session-providers`). tmux stays the kernel's own backend and the default,
  and tmux homes are unchanged. A capability declares `sessionProviders` in
  its manifest, four of its own commands (`launch`, `inspect`, `input`,
  `stop`, and optionally `inspectMany` and `check`), and `oats spawn <soul>
  --backend <name>` (a schedule's `backend`, a trigger's `spawn.backend`)
  runs the instance there. OATS keeps the home, the records, the lifecycle
  and the answers.
  - **The session-provider wire is experimental**: it is not stable until
    the follow-up change (sandbox allowances and wire 1.3), and no released
    provider speaks it.
  - A provider home records `backend` and `session: {provider, endpoint}`.
    Its status row carries `backend`, `session: {provider}` and `open` (a
    link to show instead of a terminal), and on its own host the endpoint's
    thread id; the endpoint is on its local inspect, spawn and start answers
    only, and nothing of it is relayed to another machine. `oats inspect` and
    `oats capabilities show` list `sessionProviders`.
  - A spawn holds its new home's lifecycle claim while the provider
    launches, and the home's receipt records that a launch was sent until
    its outcome is recorded (`runtime.launchSent`): a spawn or a start
    killed mid-launch leaves a home that reads as unknown, whose next stop,
    start or retire first asks the provider to stop what it started.
  - Each command of a provider runs in a process group of its own, ended
    whole at its timeout. A `launch`, an `input` or a `stop` whose `oats`
    command was killed is ended, with its group, by the next stop, start,
    input or retire of the home, before the provider is called again: it
    starts no session that OATS has no record of. A stop of a provider home
    waits for an input that is being sent (up to its timeout) before it
    asks the provider. A provider's command runs its helpers
    inside that group.
  - A stop made with OATS stays stopped: inspect answers stopped and every
    input is refused `E_SESSION_NOT_RUNNING` until the home is started,
    without asking the provider.
  - Only a lost session is resumed, in its own conversation: one stopped by
    `oats host run`'s shutdown, or one that is gone while OATS did not stop
    it. `oats session resume` sends it one notice through the provider's
    input, under a cap of 3 resumes of one home in an hour; any input to a
    lost session counts as one.
  - A provider's readiness (`check`) is asked right before every launch
    (`E_BACKEND_NOT_READY`), and `oats readiness` relays it.
  - New codes: `E_BACKEND_UNKNOWN`, `E_BACKEND_AMBIGUOUS`,
    `E_BACKEND_HARNESS`, `E_BACKEND_LAUNCH_ARG`, `E_BACKEND_NOT_READY`,
    `E_SESSION_NO_TERMINAL` (attach), `E_SESSION_PROMPT_OPEN` and
    `E_SESSION_INPUT_QUEUED` (input).
  - A routed `--backend <provider>` is sent only to a host that lists the
    feature. A kernel without it that meets a provider home only refuses.

  See [Session providers](../execution-targets.md#session-providers) and, for
  a capability's author,
  [Session providers (`sessionProviders`)](../capabilities.md#session-providers-sessionproviders).
- **A harness-package requirement can name its backends.** A `requires` row
  of a capability manifest takes `backends: ["tmux"]`, `["session-provider"]`
  or both; without it the row applies to every launch. A kernel without
  `session-providers` applies such a row to every launch, so a package that
  uses the key raises its OATS floor.

## Changed

- **Desktop: Home shows what needs you, and the Workspace page has its own row and a way back.**
  ([Workspaces](../desktop.md#workspaces))
  - **Home is one centred column.** **Needs you** comes first: each agent waiting on you, with its
    soul, its machine and its message, newest first. Eight show at most, then **Show all N**. With
    none, "Nothing needs you."
  - **One summary line** counts the rest: "24 agents · 21 running · 3 need you · 0 stopped".
  - **The workspace is one row of tiles**, each a button with its count: Agents, Souls,
    Capabilities, Teams, Machines and Automations (with the red dot while a run failed). They show
    without scrolling, even with eight agents waiting on you. The Graph tile is gone; Machines keeps
    its List and Map.
  - **Running**, under the tiles, shows five running agents, then **Show all N running**. No row
    says "running" any more: the heading does.
  - **The sidebar's pinned rows are Home, Workspace and Automations.** Opening any Workspace page
    (from a tile, the command palette, ⌘2 / Ctrl+2, or a soul's or capability's page) marks the
    Workspace row, no longer Home's. Its palette command is now **View: Workspace**.
  - **Every Workspace page says where you are, and the way back:** **Home › Workspace › Souls**
    above the tabs, and **Home › Workspace › Souls › dev** on a soul's page, each part a link. Esc
    goes up one level: twice from a soul's page reaches Home.
  - **Capabilities shows the Workspace defaults again**, above the list: the Core slots (Knowledge,
    Messaging, Tasks) and the Additional defaults, each as the list's own row.
  - **Soul cards read more clearly:** the name larger and bolder, what the soul does in muted body
    text, its agents and kind on a smaller line.

- **Desktop: the Workspace pages look like the prototype.** ([Capabilities and spawning](../desktop.md#capabilities-and-spawning))
  - **The Dark theme takes Tokyo Night's blues and greys** in the window: backgrounds, raised surfaces, ink, the blue
    accent, green, amber and red. Every text colour still meets WCAG AA; the terminals keep their own colours, and their
    cells their size. Light and Solarized keep their colours.
  - **Souls**: **Grid** | **Table** sits beside the page's title. The first line counts the souls and those with
    agents running ("You have 10 souls, 4 with agents running, …"). Group headings are small capitals with their count.
    The grid has three columns at most; a card is a calmer tile, its name in semibold, what it does on two lines, then
    one meta line, and a refused spawn says so in one quiet line.
  - **Capabilities**: a first line says what a capability is, how many there are and how many are official, and what

    the name, **core** and **default** as small pills. **Workspace defaults** stays above **All capabilities**, styled the
    same way.
  - **A soul's page and a capability's page** use the same type and spacing: a smaller title, section titles in small
    capitals, the capability and skill rows as Capabilities' rows, quieter tabs and folds.
  - **The status line shows the page's keys** on these pages: "↑↓ move · Enter open · v table · Esc Home" on Souls,
    and "Esc back" on a soul's or a capability's page.

  `oats.coordination-setup`'s `/coordination-best-practices` and

  `workstream/coordination`, `system/oats-kernel`, `system/oats-desktop`,
  `workstream/provider-integration`, `workstream/operations`,

- **OATS's own coordination capabilities teach related work.** The
  engineering expert's, the build and the maintainer's skills spawn with
  `--related-work` where they passed `--same-work`. A lead's children

  and now so does a sibling lead started for an effort that arises from the

  independent lead, and a lead a maintainer launches, still don't. The kernel
  and its injects set no default. An OATS before 0.69.23 refuses
  `--related-work`: hosts that run these capabilities need 0.69.23 or later.
  See [Related work](../desktop-cli-api.md#related-work-oats-instance-related-work).

- **Capability hooks get `OATS_BACKEND`.** Every spawn hook and launch hook
  is given the session backend the instance launches on: `tmux`, or a session
  provider's name.
- **A tmux home's row of `oats status --json` carries `backend: "tmux"`.** A
  row with no `backend` key comes from a kernel without `session-providers`,
  and reads as a tmux home's.

## Fixed

- **Claude agent panes skip the fullscreen-renderer offer.** At spawn and
  every launch, oats.core 2.16.0 adds `"tui": "default"` to a Claude home's
  `.claude/settings.json` if no `tui` key is present. Any existing value is
  kept. Agent panes use Claude's classic renderer even where Claude now
  defaults to fullscreen, and even over a user-level `"tui": "fullscreen"`;
  this keeps tmux scrollback and the renderer used by the launch-prompt
  captures. An existing project `tui` still wins. If oats.core stops adding
  the key, existing homes keep it until respawn. See
  [oats.core](../capabilities.md#oatscore-needs-input).

## Documentation

- **Launch args guidance matches the package-probe refusal.** Any non-empty
  launch-configuration `args` is refused at spawn with
  `E_LAUNCH_PROBE_UNSUPPORTED` while an active capability requires a package
  for that harness; with oats.aweb, every Claude launch has such a requirement.
  `claude plugin list --json` cannot carry those args, and `--settings` can
  change which plugins load. The supported routes are user `settings.json`
  in the Claude config selected by `CLAUDE_CONFIG_DIR` through `env`, which
  the probe carries, or a wrapper executable. `/oats-agent-permissions` now
  teaches `permissions.defaultMode: "auto"` in that user file, replacing its
  launch-args advice. See [launch configurations](../configuration.md#launch-configurations).

- **Knowledge proposals as oats.okf 6.3 runs them.** The
  [operator guide](../knowledge.md#the-flow) still said a claim
  goes only in the soul's owned nodes, that the proposer settles duplicates
  before proposing, and that the write surface is enforced. With 6.3 a quick
  search is enough, duplicates, the canonical home and the subject are the
  knowledge maintainer's, and a path outside the write surface is a `W_*`
  warning under `## Check warnings` in the PR body, which the maintainer
  resolves before merging. The authors' guide's
  [judgment and proposal](../knowledge-reference/proposal.md#judgment-procedure)
  page now says a capability may divide the work that way; the exclusions and
  the screen before delivery stay with the proposer. The
  `oats.knowledge-theory` copy changes with it.
