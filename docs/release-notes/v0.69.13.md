# OATS 0.69.13

0.69.13 lets a container deployment pass launch secrets through a private
file instead of the terminal's command line (`{ fromFile }`), provision a
harness's login token over the operator's SSH route, and manage it with
`oats harness token`; the repository ships a locked-down team agent
container image. OATS's own workspace gets its new roster of souls and
drops its `oats.engineering` pin for member copies of the engineering
coordination template; the official catalog lists the coordination
templates and moves to `oats.framework` 1.23.0, which adds
`oats.coordination-setup`. `oats sync` refuses a package pinned under
another package's id, a spawn checks the package tree against the lock,
locks are judged by their holder's identity, commands refuse unknown flags,
and doctor reports half-finished retirements and stale `souls.disabled`
entries.

## Upgrade

- **Either order of the Desktop and the CLI works.**
  [Upgrading](../upgrading.md) installs the Desktop first, and a host that
  installed the CLI first is fine too: the 0.69.13 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`, as the 0.69.12 and 0.69.11 Desktops do.
- **Package moves:** the official catalog pins oats.framework 1.23.0 (from
  1.22.1). It keeps its OATS floor; the lines in its skills that need this
  release say "from OATS 0.69.13". oats.okf stays 5.8.0 and oats.aweb
  1.37.0.

- **A home left half-retired now makes `oats doctor` report a
  `retire-incomplete` problem** (oats-project/oats#1747). That covers a
  quarantined home, and a self-retire that failed or was interrupted. Each
  problem names the command that finishes the retirement and the capability
  whose retire hook failed last. Doctor's exit status does not change: it
  exits 0 with problems, as before. A deployment with no open retirement sees
  no change.

- **`oats sync` and `oats sync --plan` now refuse a package whose
  `oats-package.json` names another package than the `packages:` key it is
  pinned under** (oats-project/oats#1759). The refusal is
  `E_PACKAGE_INTEGRITY` with `why: "package-id"`. Its message names both ids
  and the line to write in place of the key, then `oats sync`. A refused sync
  writes nothing, and a lock that already holds such an entry is refused at
  the next sync. Existing homes, and spawns from the current lock, keep
  working until the line is fixed. Every version in the official catalog
  names its own id. Before upgrading, check each `git:` pin in `packages:` on
  the version you are leaving: the repository's `oats-package.json` at that
  ref must say `"package": "<the key>"`
  ([`oats sync`](../packages.md#oats-sync--the-one-command-for-the-common-path)).

- **After upgrading, remove a sweep lock directory the earlier OATS left.**
  A directory at `~/.oats/session-resume/lock` is the earlier OATS's lock.
  This OATS never judges or removes it: `oats session resume` refuses it
  with `E_RESUME_LOCK_STUCK`, and no sweep starts anything on the machine
  until you remove the directory by hand, once no earlier `oats` is running
  there. `oats doctor` reports it. An earlier OATS on the same machine takes
  the new lock over once it is a minute old, also from a sweep that still
  runs, so run one OATS version per machine.

- **After upgrading, remove a start lock directory an earlier OATS left.**
  An earlier OATS made the directory `<home>/.oats-start.lock` for each
  session start and could leave it behind when the start was killed. This
  OATS makes nothing there: `oats session start` and `restart` refuse a
  home with that directory with the new code `E_SESSION_START_LOCK_STUCK`,
  naming it, and never remove it; `oats instance upgrade` refuses it too,
  naming it. Remove the directory once no earlier `oats` is running on the
  machine. The resume sweep reports such a home as a refused start
  (`start-refused`, with the code) instead of skipping it as one where a
  start is running. The Desktop and `oats tui` show it as a start that
  started nothing, with a sentence that says to remove the lock its message
  names once no earlier OATS is running, since waiting will not clear it.

- **Earlier OATS versions on the same machine still judge a cache write lock
  by its pid alone.** A cache that an earlier `oats` also writes keeps that
  behaviour for the locks it meets: it waits for a lock whose pid another
  process holds, and so does this OATS for a lock the earlier one wrote,
  whose record names no boot or start time. Run one OATS version per
  machine to have every cache write lock judged by its holder's identity.

- **A deployment of OATS's own workspace takes four hand steps, in this order.** Names written for the package's reviewer, `oats.engineering/code-reviewer`, now name the workspace's `code-reviewer` soul.
  1. **`souls.launch`.** Remove the old key:

     ```sh
     oats soul launch remove oats.engineering/code-reviewer
     ```

     The soul's own launch, pi with `github-copilot/gpt-6.1-sol`, then applies, unless the machine has a `souls.launch."*"` entry: that one wins over the soul's own launch, for the reviewer as for every soul without an entry of its own. Check what the reviewer will run on with `oats spawn code-reviewer --preview`. That preview, like every spawn that names no launch, of a soul with no `souls.launch` entry of its own, is refused while `souls.launch` holds any other key that names no soul: remove or re-point each such key first. A reviewer runs on a model family other than its developers'. Where the `"*"` entry, or any other choice, would put it on theirs, give the reviewer its own key: `oats soul launch set code-reviewer --harness <harness> --model <model>` (or `--launch-config <name>`).

     Left in place, the old key stops spawns. `oats doctor` shows `E_LAUNCH_PREFERENCE_UNMATCHED: oats-local.yaml souls.launch names "oats.engineering/code-reviewer" (nearest: code-reviewer)`. Its fix line pins a soul first, then removes the key; here removing the key is enough. Every spawn that names no launch, of a soul with no `souls.launch` entry of its own, is refused with that code, and nothing is created or started. A spawn that names its launch (`--harness` or `--launch-config`) still runs.
  2. **`souls.disabled`.** No command writes it. In `oats-local.yaml`, change `oats.engineering/code-reviewer` to `code-reviewer`. A stale entry **fails open**: it disables nothing, so the renamed `code-reviewer` spawns again on that machine, and the spawn doesn't refuse. `oats doctor` reports the stale entry (`disabled-soul-unmatched`).
  3. **Team patterns.** They are the workspace's `souls:`, and OATS's has only `"*"`, which covers `code-reviewer`. Nothing to change. `oats soul teams code-reviewer` shows the `oats` team, from `"*"`.
  4. **Schedules and triggers.** Find any that spawns the old soul with `oats schedule list` and `oats trigger list`. `oats schedule test <id>` reports `soul oats.engineering/code-reviewer does NOT resolve (E_SOUL_UNKNOWN)`, and the job spawns nothing; `oats trigger test <id>` checks its soul the same way. Change each to `code-reviewer`:
     - a host schedule: `oats schedule update <id> --file <spec.json>`, with `"agent": "code-reviewer"`;
     - a local trigger: `oats trigger remove <id>`, then `oats trigger add --file <trigger.json>`, with `"soul": "code-reviewer"` in its `spawn`;
     - a workspace schedule or trigger: in its file in Git.

     A new schedule that names the old soul is refused when it is added.

  Then run `oats doctor`, after this or any soul rename or removal, and fix what it reports: a stale `souls.launch` key and a stale `souls.disabled` entry each show there.
- **Running instances keep their copies.** An instance spawned before this change, the package's `code-reviewer` included, keeps v1.18.0's modules until it is retired and respawned. A respawn picks up the member copies.

- **A deployment of OATS's own workspace moves onto the new souls, by hand.**

  1. **Respawn the live homes onto the new souls,** once each has finished or handed off its effort (`oats status` lists them). For each home of `oats-expert`, the area experts, `oats-kernel-developer` or `oats-integrations-developer`:
     ```bash
     oats retire <name> --plan
     oats retire <name>
     ```
     New work starts on the successors, `oats-engineering-expert` and `oats-developer` (from your dispatcher, below). A home of `oats-engineering-expert`, `oats-developer` or `oats-desktop-developer` spawned before this change takes the new texts the same way: retire it once its work is done, and spawn a fresh one for the next effort.
  2. **Start the dispatcher,** one standing instance for each person who wants one:
     ```bash
     oats spawn dispatcher --name <person>-dispatcher --task-file <who it serves.md>
     ```
     It starts a fresh expert of the right soul per effort, introduces its lead and steps aside.

## Added

- **`oats doctor` and `oats doctor --json` list each retirement left open**
  as a `retire-incomplete` problem in `problems[]`, `{code, message,
  remedy}` (oats-project/oats#1747). The remedy is `oats retire <name> --home
  <home>`, shell-quoted, and names the capability whose retire hook failed
  last. A retire that is running, or whose state cannot be read, is not
  listed. Neither is a spawn in progress, or an outcome whose home is gone,
  which `oats status` still lists
  ([doctor `problems[]`](../desktop-cli-api.md)).

- **A retire hook's warnings stay readable after the retire, as `retire-warning`
  events** (oats-project/oats#1749). A retire hook can succeed and still name
  an action someone must take. Until now that warning was only in the retire's
  answer, and was lost once the caller moved on.
  - Each warning of the retire hooks is now one `retire-warning` row, `data:
    {message}`, in the instance's workspace log. `oats instance events
    <instance> --json` reads it after the home is gone.
  - The rows are written as soon as the hooks return. A retire that then
    refuses or ends quarantined keeps them, and each retry of the hooks adds
    its own.
  - A retire whose hooks warn nothing writes none. The retire's answer and the
    `retired` event are unchanged. Older clients read the new kind as an
    unknown kind
  ([Events](../desktop-cli-api.md#events)).

- Launch configuration environment values accept `{ fromFile: /absolute/path }`.
  Each start reads a regular UTF-8 file on its execution host and removes one
  trailing line ending, preserving a UTF-8 BOM. Invalid UTF-8, missing,
  unreadable, NUL-containing or nonregular files
  refuse with `E_LAUNCH_ENV_MISSING` and a provisioning remedy. Preview, list
  and recipes contain references only; resume checks compare keyed digests.
- Both `fromEnv` and `fromFile` values now reach the pane through a private
  per-start file, removed by the launcher before the harness runs. This removes
  the existing `fromEnv` exposure in tmux process arguments. A subsequent start
  removes abandoned handoff files, including when it needs no references.
- `fromFile` is for credential values. Directory selectors require a literal
  or `{ fromEnv: NAME }`; validation names the selector and remedy.
- With references, the private handoff runs the pane wrapper through `/bin/sh`.
  Harness arguments already pass through the native recorder's POSIX shell;
  capability launch contributions are parsed arguments, not shell programs.
- File sources are capped at 64 KiB, including a final newline, with bounded
  reads. Refusals name the file and the missing, type, permission, encoding, NUL
  or size problem while keeping `E_LAUNCH_ENV_MISSING`.

- Claude starts check the effective configuration directory for a `/login`
  credential. When OATS also sets `CLAUDE_CODE_OAUTH_TOKEN` (literal, `fromEnv`,
  `fromFile` or a launch hook), the start refuses with
  `E_CLAUDE_LOGIN_CREDENTIAL`, naming the exact credential file and
  `oats harness token set claude`. Without an OATS-set token, a personal
  `/login` credential is allowed silently. Remove the `/login` credential before
  starting on the token route. Inherited pane tokens do not trigger refusal.
- Spawn preview and apply check the predictable launch configuration before
  creating a home, worktree or identity.
  Hook-supplied selectors and tokens are checked once their environment is
  known, and the actual pane is checked again before dispatch.
- The final credential check follows the harness selected for this start,
  including a switch between Claude and another harness. Hook-supplied
  directory selectors are covered at preview, spawn and start.

- `oats server add` and `oats server connect` accept `--operator-ssh <alias>`.
  The optional operator route follows the same validation rules as `sshHost`
  and appears as `operatorSshHost` in `server list` and connect's registration.
  It lives in `~/.oats/server-operator-routes.json`, under the same servers
  lock, so `servers.json` stays readable by older kernels, including Desktop's
  bundled kernel. Older kernels never read the separate file.
- `--replace` keeps the operator route unless `--operator-ssh` sets it again
  or `--no-operator-ssh` clears it. `server remove` deletes its route too.
  Existing commands and saved instance targets keep using the agent's SSH alias.
- A fresh registration never inherits an orphan operator route left by an
  older kernel's remove. On an unchanged agent target, an operator-only update
  preserves `servers.json` bytes; an answered `--replace` can still refresh a
  stale workspace key without a false concurrency warning.

- `oats harness token set|status|remove <harness> --server <id>` uses the
  separate operator SSH route and forced-command credential receiver.
  `set --stdin` supports Claude setup-tokens and Codex, pi and opencode
  API keys, without credential arguments, output or client files. A missing
  operator route refuses; it never falls back to the agent route or reuses
  its authenticated connection. Malformed or oversized replies fail closed,
  and remote refusal text is escaped for terminal output.
  Unknown server ids refuse before SSH, including when an orphan operator route exists.
- The npm package includes `share/oats-login-receive`; see
  [receiver installation](../servers.md#install-the-credential-receiver)
  for Python 3, the root-owned configuration and the restricted SSH key.
- Rotation lists sessions of the same harness started before or during the
  receiver's reported replacement second;
  they pick up the new value at their next start. Nothing restarts
  automatically. A roster failure after installation is a warning, not a
  failed install. Claude interactive capture is unavailable, and refreshing
  browser sign-ins do not fit the read-only credential model.

- **`E_RESUME_LOCK_STUCK`: a sweep lock that needs a person has its own
  code, and `oats doctor` reports it.** `oats session resume` answers it,
  never `E_RESUME_BUSY`, when the lock cannot be taken and no sweep is known
  to run: a record that cannot be read, a holder that cannot be told to be
  running or gone, a gone holder's record that cannot be taken over, or the
  earlier OATS's lock directory. The message says which it found and what
  to do about it, and `error.details` is `{lock, found}`. `oats doctor`
  lists the same states as a `resume-lock-stuck` problem, reading the lock
  without taking it
  ([The machine sweep](../desktop-cli-api.md#the-machine-sweep-oats-session-resume)).

- **The setup expert now knows how an organisation's agents should work together.** A new capability in oats.framework, `oats.coordination-setup`, holds OATS's coordination practices (`/coordination-best-practices`) and four skills for shaping them to one organisation:
  - `/adapt-to-the-organisation` runs at onboarding.
  - `/design-the-roster` proposes the souls: an expert per way of working with areas as its knowledge nodes, developer souls by environment, reviewers, maintainers when a lane needs one, a dispatcher per person who wants one, and retire rules.
  - `/set-landing-rules` writes, per lane, who merges on which agreement, who gives the green light to open a PR, and a merge path every lead can reach.
  - `/review-the-setup` proposes the smallest change when a signal says the setup no longer fits.

  The package soul `oats-setup-expert` composes it. Another soul uses it by naming `oats.coordination-setup: { from: package }`.

- Desktop logs one startup disposition for a launch carrying `--instance`,
  including why no selection request could be sent. Linux output capture is
  documented in [Desktop troubleshooting](../desktop.md#troubleshooting).

- **OATS's souls are split by way of working, not by area.** OATS's workspace gains a front door, two experts and one developer:
  - **`dispatcher`**: each person's front door, from the engineering template (template-v2.1.0). It starts a fresh expert of the right soul per effort, introduces its lead and steps aside. Start one standing instance for each person who wants one: `oats spawn dispatcher --name <person>-dispatcher --task-file <who it serves.md>`.
  - **`oats-engineering-expert`** (succeeding `oats-expert`): every engineering effort, in every area (the kernel and the CLI, the Terminal UI, the Desktop, the provider packages, operating a deployment, the docs). It shares `oats-expert`'s knowledge owner and node, `oats/oats-expert`, and reads each area's node per task. Until the knowledge base is organised by subject, an area lesson goes into its own node, with its area named in the concept.
  - **`oats-product-expert`** (succeeding `market-research-expert`): vision, direction, users and positioning, research and trials, the README and the concept pages. It writes a brief and hands it to an engineering expert at an exact version. It shares `market-research-expert`'s knowledge owner and node, `oats/market-research-expert`, and names each direction decision for the maintainer's node in its hand-back.
  - **`oats-developer`** (succeeding `oats-kernel-developer` and `oats-integrations-developer`): the kernel and the CLI, the Terminal UI, the provider package repositories and the docs. `oats-desktop-developer` keeps the Desktop.

- A reviewable agent container image, Compose service and Docker acceptance
  script with pinned CLIs, arbitrary non-root UID support, read-only root,
  SSH public-key access and explicit isolation evidence. See the
  [container contract](../container.md) for mounts, deployment and the
  prerequisites for live two-seat authentication.

## Changed

- **The getting-started skill sets npm's per-user folder and its PATH line in two commands** (oats-project/oats#1665). Step 2 named npm's per-user prefix in its text beside the PATH line's command, without saying to keep them apart, and an agent ran both as one command. Claude Code's auto mode refused it as persistence, even though the person's yes named both changes. Each is now its own command, under the name step 1's list gives it. Step 8 also says that the warning from Git older than 2.45 about whole-tree fetches is expected and harmless, in its once-per-command form and in the older once-per-repository form, and that Git 2.45 or later removes it.

- **Joining an existing workspace takes one paste.** With oats.aweb 1.36.0 or later and aw 1.36.53 or later, the getting-started skill has the joiner paste only the invite token: `oats aweb setup --soul S --invite-stdin --name A` reads the team and the service from the invite and refuses one that doesn't fit before redeeming it. The teammate no longer passes a service URL. Older versions keep the labelled form with `--join` and `--service` ([awebai/oats-aweb#56](https://github.com/awebai/oats-aweb/issues/56)).

- **A self-retire retries a cleanup that retire hooks alone left incomplete**
  (oats-project/oats#1747). When the completion of `oats retire --self` ends
  with the home quarantined, owing retire hooks and nothing else, it runs the
  retire again up to three times: about 1, 5 and 15 minutes after each
  failed attempt.
  - A retry whose hooks pass removes the home and leaves nothing behind.
  - After the last failed attempt the outcome is as before, plus `attempts`.
    The marker, the quarantine and the one `retire-refused` event stay.
  - Every attempt records its own `retired` event with its hooks.
  - A quarantine that also owes Git steps, directory preservation or an
    orphaned work directory is not retried.
  - While the completion waits, `oats status` reads the retire as `running`.
    Another retire of the home is refused with `E_LIFECYCLE_BUSY`, for up to
    about 21 minutes after a hook failure. The refusal names the next attempt
    and the earliest time the last one starts.
  - Plain retires are unchanged
  ([Self-retire](../souls-and-instances.md#self-retire-hook-retry)).

- **A `launch-warning` or `retire-warning` row stores its message made safe
  and bounded** (oats-project/oats#1749). Control, bidi and hidden characters
  are replaced with U+FFFD, and the text is cut to 2048 UTF-16 code units
  ending in `…`. A warning that is not a string is stored as its JSON. The row
  shape is unchanged, and the answers' `warnings` keep each warning as it was said
  ([Events](../desktop-cli-api.md#events)).

- **A `souls:` pattern that matches no soul now warns `team-soul-unknown`**
  (oats-project/oats#1759). A `<prefix>/*` key in `oats-workspace.yaml`
  `souls:` whose prefix is no member or package with souls here (a typo, or a
  package that was renamed or dropped) was ignored without a word; exact keys
  already got the warning.
  - It shows where an exact key's warning shows: `oats teams` and readiness
    (`checks.configured`, not required), with the same code, `severity`,
    `key` and `at`. Its message says the pattern matches no soul.
  - The fix: correct the prefix to a member's or package's name (`oats souls`
    lists them), or remove the key. A pattern that matches at least one soul,
    and `"*"`, stay silent. Exact keys' message and fix are unchanged
  ([Workspaces](../workspaces.md), [Team readiness items](../desktop-cli-api.md#team-readiness-items)).

- **After a pin is removed or renamed, run `oats doctor`.** `/oats-package-pins` ("Change a pin") and [packages](../packages.md) now say: after removing or renaming a pin, or any soul it provided, run `oats doctor` on each deployment and fix what it reports, and check `souls.disabled` by hand. A `souls.disabled` entry that names a soul that no longer exists fails open: it disables nothing, so the soul it was meant to keep off spawns again under its new name.

- **A session start makes no `.oats-start.lock` directory.** Two starts of
  one home already excluded each other through the home's lifecycle claim
  (#1602); the start lock directory was a second guard that a killed start
  left behind, after which every start of the home answered
  `E_SESSION_START_BUSY` until it was removed by hand. A start now only
  reads that path: a package upgrade that has not finished is refused as
  before, naming its same-key retry
  ([Desktop CLI API](../desktop-cli-api.md)).

- **"CI green" in OATS's landing rules no longer holds with every check red.** The rules defined it as every check the forge requires at a head having succeeded. OATS's repositories require no check on their default branches, so that definition was empty. CI green at a head now means at least one check ran there, every check the forge requires is among them, and every check that ran succeeded: none failing, none pending. A head where no check ran isn't green. That holds with or without required checks, and a check that ran without being required can't fail on a green head either. Every skill that reads "CI green" (a developer's "Ready", a maintainer's read and merge, a release's source) takes it from the landing rules, so they change with it. A running instance takes the change up as the landing rules say a change reaches one: whoever lands it tells each standing instance and each open effort's lead, at its commit, and each records it in its state file. A respawn picks it up too.

- **The setup expert's coordination practices follow the templates' v3 way of working** (`oats.coordination-setup`, in `oats.framework`), at the engineering template's template-v3.0.1 and the research template's template-v2.0.0. `/coordination-best-practices` now teaches what an organisation's copy of a template will say:
  - **The lead decides who builds each spec,** and builds it itself by default; a developer earns its place by context, parallel work or specialisation, and a large feature always goes to developers. In research, the lead decides who researches each angle the same way, a question with several angles always goes to researchers, and a fresh verifier checks every claim, the lead's own included.
  - **A lead's children are helpers, each with one closed task** (a probe, a spec or a scoped piece), with their bounds and what they send back. Another area's step stays in the effort, never a second lead; a related effort's lead is the first lead's sibling, and the person is told its name. Every child is spawned `--same-work`.
  - **Whoever builds a change runs its review loop,** and nothing lands without a fresh review: a one-line docs fix skips the local loop, not the review. The reviewer's severity decides whether the same reviewer re-reads a fix or a fresh one does, and a verdict that doesn't say what it checked is not a review. A lead starts a missing maintainer without asking, and tells the person what it is.
  - **Every role's briefing says, in capitals, to keep loading its skills** as the work goes on; the setup expert's coordination briefing says the same.
- `/set-landing-rules` writes those rules as the default (who builds, when a review carries to a new head, the one-line docs fix, the green light for a lead's own change); `/design-the-roster` gives developers, reviewers, maintainers and the retire rules the same wording and names the research souls; `/adapt-to-the-organisation` names the research template for work that ends in a report and checks the copied role skills agree on who builds; `/review-the-setup` gains two signals, a lead that sends every small change to a developer or builds a large feature alone, and verdicts that don't say what they checked.

- **Onboarding adapts the coordination template with these practices.** `/oats-tailor-workspace` shapes a workspace's coordination template with `/adapt-to-the-organisation`: the roster of souls (`/design-the-roster`), the landing rules (`/set-landing-rules`) and, with several people, the ownership record. The capability notes the template version it started from.

- **Onboarding starts coordination from OATS's template repositories.** Coordination ships as templates, not packages. `/adapt-to-the-organisation` and `/oats-tailor-workspace` now start each group from the closest template repository at its latest `template-v*` tag and follow its `ADAPTING.md` in order: they check for capability ids the workspace already has before copying (a pin of the frozen `oats.engineering` moves by the template CHANGELOG's "From v1.18.0"; an earlier copy is upgraded in place), keep the template's `LICENSE` and `THIRD-PARTY-NOTICES.md`, keep an adapt marker only for a point that waits on a person, and record the release in each copied capability's description and in `capabilities/TEMPLATE-RELEASE`. The first template is `oats-project/oats-engineering-coordination`, at `template-v2.1.0`. The skills name it directly, so they find it on every kernel `oats.framework` admits; from this kernel release, `docs/official-catalog.md` lists the templates under "Coordination templates". `/review-the-setup` ports a later release from that record.
- **The package `oats.engineering` is frozen at v1.18.0.** Existing pins keep resolving through its catalog entry and aliases; its repository gets no further releases, and the engineering template lives in its own repository.
- **The coordination practices say which children are OATS instances.** `/coordination-best-practices` now sends proper work (an investigation or test the plan rests on, a review, work that needs a soul's knowledge or an environment) to OATS children, and allows the harness's own subagents (in Claude Code, pi or Codex) for small tasks that directly help the lead, when the person asks, or in a multi-agent workflow mode such as Claude Code's ultracode. A child that checks work runs on a different model from the agent whose work it checks, and the developer, not the expert, launches its fresh reviewer for each round. `/design-the-roster` gives the reviewer soul a launch on a model from a family different from the developers', `/oats-tailor-workspace` gives that soul its own launch entry where the machine's `souls.launch."*"` would replace its model on the same harness, and checks its effective model's family in its preview, and `/set-landing-rules` lets a lane exempt a lead's one-line docs fix or a maintainer's release prep from the review loop, never where every commit must pass a review round.
- **Probes test theories and approaches.** `/coordination-best-practices` adds testing a theory on small, concrete cases to a probe's questions. Where a plan can go more than one way, the lead probes the competing approaches in parallel and compares them on evidence, records every approach tried, and has a claim the plan rests on checked by another probe with fresh context, never by the probe that made it.

- A Desktop launch with `--dir <deployment> --instance <name>` opens the named
  running local instance's terminal tab in the main area, through the same
  viewer path as a roster click. Keyboard focus stays on the roster row;
  the launch sends no input and starts nothing. Stopped, unknown, held,
  unavailable or stale rows stay selected only, without a Start dialog.

- **Inside a container, `oats session resume` counts a boot per run of the
  container** (oats-project/oats#1792). A container shares its host's kernel, so the kernel's boot id,
  which the sweep read as the boot, stayed the same when the container was
  stopped and started, although every session in it was gone. With
  `~/.oats` on a volume, the third restart of a container within one host
  uptime used up the 3 sweep starts a home has per boot, and the sweep then
  answered `keeps-getting-lost` for sessions lost with the container; a
  session lost with a container that stayed down for a day or more was
  answered `not-seen-recently`, since the 24-hour clause of one boot applied
  across the restart. The boot in a container is the kernel's boot id
  together with the start time of the container's PID 1 (`/proc/1/stat`),
  which is the same all through one run and another in the next. OATS takes
  itself to be in a container when `/.dockerenv` or `/run/.containerenv`
  exists or `KUBERNETES_SERVICE_HOST` is set. On a Linux host and on macOS
  the boot is what it was, and the sweep's records stay valid; in a container
  the first sweep after the upgrade starts a new count
  ([Execution targets](../execution-targets.md#the-sweep)).

- **A lock left by a command that was killed no longer stops the commands
  after it.** The locks of the host scheduler (`~/.oats/schedules/host.lock`,
  `registry.lock`, a deployment's `scope.lock`), of the server registry
  (`~/.oats/servers.lock`), of this computer's deployments list
  (`~/.oats/config/deployments.lock`) and of a deployment's `oats-local.yaml`
  (`.agents/locks/local.lock`) were directories that nothing but their holder
  removed: a tick or a command killed with SIGKILL, by the out-of-memory
  killer or by a reboot left its lock behind, and every later command
  answered `E_SCHEDULER_BUSY` (or `E_SERVERS_BUSY`, `E_DEPLOYMENTS_BUSY`,
  `E_LOCAL_BUSY`) until someone deleted the directory by hand, so the
  per-minute scheduler stopped for good after one killed tick. Each lock is
  now a file that names its holder by pid and start time, and the next command
  takes over a lock whose holder is gone. A holder that is still running is
  never taken over. A SIGINT or SIGTERM that arrives inside a locked section
  waits for it: the section completes, the lock is released, and the signal
  then ends the command (it was lost before, and the command ran on). Three cases still need the operator, and the message says
  which it found and names the path: a lock file whose record is unreadable
  (remove the file), a holder that cannot be told to be running or gone
  (check that pid by hand, then remove the file), and a lock directory written
  by an earlier kernel, which is never removed for you (remove the directory
  once no older oats is running) ([Schedules](../schedules.md#files)).

- **`oats instance git` and `oats instance diff` run no filter driver the
  work tree's repository configures.** A repository's own configuration,
  which an agent working in the tree can write, can define
  `filter.<name>.clean` or `filter.<name>.process` and select it with a
  `filter` attribute (`.gitattributes`, or `info/attributes` in the Git
  directory). Git runs such a command during a `git status` or a `git diff`,
  as whoever runs it. Every Git command of the observation that reads a
  work-tree file is preceded by a read of the configuration
  (`git config --list`, which runs nothing), and each filter driver it
  defines is overridden to no command.
  - The observation of a repository with no filter driver is unchanged.
  - A file a filter applies to (a Git LFS file, for one) is compared as its
    bytes are in the work tree: rewritten, it reads as `changed` even when
    its filtered form is what is stored, and its diff is the stored form
    against the work tree's bytes. The observation says so in a note.
  - A driver whose name cannot be passed on Git's command line (it holds `=`
    or is not UTF-8) refuses the read with `E_GIT_FAILED`.
  - Not covered: a driver written between that read and the Git command, and
    a filter that a submodule's own configuration defines, which matters
    where the agent and the reader of its worktree are separate system users
    ([Git and diff](../desktop-cli-api.md#git-and-diff)).

- **A spawn refuses a package whose content is not what the lock records.**
  `oats-lock.json` pins each package to a `commit` and to the `integrity` of
  its tree, but a spawn compared neither with what it copied. A lock whose
  commit and integrity disagreed (a hand edit, a bad merge), or a package
  copy that changed in this computer's remote cache, spawned without a word.
  - `oats spawn`, and `oats spawn --preview`, now digest the tree of every
    package the soul composes a capability from, at the locked commit, and
    refuse a mismatch with `E_PACKAGE_INTEGRITY` before anything is written:
    no soul copy, no worktree, no instance home. The message names the
    package, the commit, the lock's digest and the one computed, and
    `details` is `{package, version, commit, expected, actual}`.
  - The digest is taken once per package version on a computer. A tree that
    matched is recorded under the remote cache (`.verified/`), with the state
    of the cached repository it was read from, and a later spawn digests
    again only when a file of that repository was added, removed, replaced or
    rewritten since. The records are the kernel's own and safe to delete.
  - `oats instance upgrade` already made this comparison for the packages it
    moves a module to. Its refusal now carries the same message, and its
    `details` gain `version` and `commit` beside `package`, `expected` and
    `actual`
    ([The integrity check at spawn](../packages.md#the-integrity-check-at-spawn)).

- **`oats retire` and `oats worktree remove` run no filter driver the
  repository configures.** A repository's own configuration, which an agent
  working in the tree can write, can define `filter.<name>.clean` or
  `filter.<name>.process` and select it with a `filter` attribute
  (`.gitattributes`, or `info/attributes` in the Git directory). Git runs
  such a command during a `git status`, as whoever runs it, and a retire and
  a removal both ask for one: a retire of the worktree, of a repository
  under it and of its recovery copy (and a spawn, for the baseline a retire
  compares with); a removal for its own status, inside `git worktree remove`
  and when it compares an unregistered tree's surviving files. Each of
  those commands is preceded by a read of the configuration
  (`git config --list`, which runs nothing), and each filter driver it
  defines is overridden to no command, as `oats instance git` does it.
  - A retire or a removal in a repository with no filter driver of its own
    is unchanged. A driver that the operator's global or system
    configuration defines runs with the operator's command, also when the
    repository defines one of the same name (`git lfs install --local`):
    the repository's values for that name are replaced by the operator's.
  - A file a repository's filter applies to is compared as its bytes are in
    the work tree. A clean filter could make a rewritten file read as
    unchanged: `oats retire --discard-worktree` then removed the worktree
    with that file in it and wrote no recovery, and `oats worktree remove`
    removed the tree. Such a file is uncommitted work: the retire copies it
    to the recovery, and the removal refuses with `E_WORKTREE_DIRTY`. A
    file whose size and times are the ones the index recorded still reads
    as unchanged.
  - A driver whose name cannot be passed on Git's command line (it holds `=`
    or is not UTF-8) is refused before Git runs. A retire answers
    `E_WORK_INSPECTION_FAILED` before its hooks, with `--discard-worktree`
    and `--force` too; a spawn into a worktree of that repository is
    refused and rolled back; a removal answers
    `E_WORK_PRESERVATION_FAILED` with the tree and its record kept.
  - A retire that copies a worktree compares the copy's status with the
    worktree's, and the copy has none of the repository's configuration.
    For a file a repository's filter applies to, the two can disagree, and
    the retire then refuses with `E_WORK_PRESERVATION_FAILED` and removes
    nothing. That is so only for a driver the repository alone defines,
    and was so before (an untouched file whose stored form is the filtered
    one).
  - Not covered: a driver written between that read and the Git command,
    and a filter that a submodule's own configuration defines, which matters
    where the agent and whoever retires or removes its worktree are separate
    system users
    ([Filter drivers](../souls-and-instances.md#retire-filter-drivers)).

- **`oats session resume` takes over the lock of a sweep that is gone at
  once, and never mistakes another process for it.** The sweep's lock
  (`~/.oats/session-resume/lock`) named its holder by pid alone within one
  boot: when a sweep was killed and its pid went to another process, every
  later sweep answered `E_RESUME_BUSY` until that process ended, and a sweep
  killed just as it took the lock stopped the others for a minute. The lock
  is now a file that names its holder by pid, start time and boot, as the
  kernel's other locks do: the next sweep takes over a lock whose holder
  exited, was killed (a container's stop included) or took it in another
  boot, with no wait. A sweep that is still running is never taken over, and
  a second sweep answers `E_RESUME_BUSY` as before
  ([Execution targets](../execution-targets.md#the-sweep)).

- **The commands that change state refuse a flag they do not define**
  (oats-project/oats#1791). `oats instance stop`, `oats instance upgrade`,
  `oats worktree add` and `remove`, `oats session start` and `restart`,
  `oats schedule remove`, `run`, `enable`, `disable`, `reconcile` and
  `host uninstall`, `oats trigger remove`, `enable` and `disable`, `oats
  server remove` and `forget`, `oats package add` and `remove`, `oats
  launch-config set` and `remove`, and `oats automations refresh` read the
  flags they knew and ignored every other one, so a typo of a protective
  flag did the unprotected thing: `oats instance stop <instance> --apply
  ... --no-recursve` also stopped the recorded children, and `oats instance
  upgrade <instance> --undoo --plan` planned the forward upgrade.
  - Each of them now refuses, with `E_BAD_ARGS` and before anything
    happens (before a plan is read, a file is written, a session is stopped
    or started, and before a `--server` command is sent to its host), a
    flag it does not define, a value given with `=` to one of its switches
    (`--undo=yes`), and an argument after the last one it takes. The message
    names the flag and the command and prints the command's usage
    (`oats instance stop: unknown flag --no-recursve`); under `--json` the
    envelope carries `error.details.flag` or `error.details.argument`.
    `oats retire` refuses the same way, with the same words as before.
  - A script that passes one of these commands a flag it never defined gets
    the refusal where the flag was ignored: remove the flag. Among them:
    `--dir` on `oats session start` and `restart` (they take `--home`),
    `--stop-grace` on `oats session start` (it is `restart`'s), and
    `--server` on `oats trigger remove`, `enable` and `disable`, which have
    no route and changed the trigger on this machine. The flags each command
    defines are listed in
    [The flags a command defines](../desktop-cli-api.md#command-flags).
  - The refusals some of these commands made of one flag in their own words
    (`--server` on `oats instance upgrade`; `--server`, `--dir` and `--home`
    on `oats worktree`; `--home` and `--soul` on `oats launch-config set`
    and `remove`; `--resume` on `oats session restart`) keep their words,
    carry `error.details.flag`, and now also come before a `--server`
    command is sent. `oats worktree remove` given `--branch`, `--base`,
    `--repo` or `--preview` answers `unknown flag` with its usage.
  - `oats retire --json <instance> ...`, with `--json` before the
    instance, answers its refusal as one envelope.
  - `oats retire --json` with no instance answers `E_USAGE` with the usage
    line as one envelope, as a missing argument of other commands does; it
    printed the usage on stderr and no envelope. Without `--json` it prints
    the usage line, as before.
  - A command of the table given `--server` and missing its argument (`oats
    retire --server build` with no instance, `oats schedule remove --server
    build` with no id) answers `E_USAGE` with its usage line on this
    machine and sends nothing; it was sent to the host.
  - `E_USAGE` is one of the codes `oats retire` and `oats instance stop`
    answer only before any effect
    ([the table](../desktop-cli-api.md#before-effect-codes)): a client may
    read it as "refused, nothing happened". The Desktop does: a stop or a
    retire it applies that answers `E_USAGE` shows as refused, "Invalid
    lifecycle request.", with the usage line in Details, where it showed an
    unknown outcome with no description.

- **A cache write lock whose holder is gone no longer stops writes to the
  cache when its pid belongs to another process.** The cross-process write
  lock of a remote cache repo (`<cache>/.locks/<repo>.lock`) named its holder
  by pid alone: when the holder died and its pid went to another process
  (after a reboot pids start low again), every write to that cache waited
  out the whole deadline and was refused with `E_REMOTE_UNREADABLE`
  (`reason: "cache"`) until that process ended, which could take days. The
  lock's record also names the boot it was taken in and its holder's start
  time, as the kernel's other locks do, and a lock taken in another boot, or
  whose pid runs with another start, is reclaimed at once. A holder that is
  still running is never taken over. The refusal for a lock that is held
  says to check whether the named pid is an oats process, and that once no
  oats process holds it, the lock file it names is safe to remove
  ([Implementation](../implementation.md)).

- **`oats-getting-started` installs the Desktop again after the repository moved to `oats-project`.** After the transfer, `gh attestation verify <file> --repo awebai/oats` resolves to `oats-project/oats`. The attestations of releases up to 0.69.12 stayed with the `awebai` organisation, so the verify got `HTTP 404`, step 3 never printed `VERIFIED`, and no new onboarding installed the Desktop. Step 3 now downloads from `oats-project/oats` and verifies with `--repo oats-project/oats`. For versions up to 0.69.12 only, it falls back to `--owner awebai`. Each form accepts only its own repository's release workflow, run for the release's tag (`--signer-workflow`, `--source-ref`). The two forms are grouped, so a failed download or checksum still never prints `VERIFIED`. The checksum now also fails when `SHA256SUMS.txt` has no line for the file: on macOS, `sha256sum` passes empty or malformed input ([The Desktop](../desktop.md)).

- **The Desktop explains a refused sync's `E_PACKAGE_INTEGRITY` for what it
  is** (oats-project/oats#1765). The sync sheet said every such refusal meant
  a moved tag or a branch, including a lock whose capabilities or souls were
  edited and a package whose manifest names another id. It now reads the
  kernel's `why`: a branch pin says to pin a tag or a full commit; a
  manifest naming another id says to change the pin as Details says; an
  edited lock says to remove that package's entry from the lock file. A moved
  tag, or a case this Desktop doesn't know, gets the general meaning: the
  package doesn't match what the workspace file or the lock records for it.
  The kernel's message stays under Details
  ([`oats sync`](../desktop-cli-api.md#oats-sync)).

- **On macOS, the boot id is read with the system's `sysctl`, whatever the
  caller's `PATH`** (oats-project/oats#1821). It was read with the first `sysctl` on `PATH`, so under a
  `PATH` without `/usr/sbin` (a scheduled job, a reduced environment) it read
  none. The boot rule was then off without a word: the resume sweep's count
  of starts per boot and its lock, and the cache write lock's holder check,
  judged by process alone, and a lock taken before a reboot could be held by
  a pid the new boot reused. The system directories the kernel runs its tools
  from are `/usr/bin`, `/bin`, `/usr/sbin` and `/sbin`, in that order.
