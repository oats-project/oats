# OATS 0.69.15

0.69.15 gives a host without a timer, a container among them, the kernel's
periodic work: `oats host run` is one foreground process that resumes
sessions at start, runs the schedules every minute, and stops the agents in
order on SIGTERM, so the next start resumes them. A spawn routed through a
server keeps its task off both machines' command lines. And a spawn, a
retire or a stop that was killed half-way (a container that stopped, a
dropped ssh link) now ends in a state the next command finishes, instead of
a home with no record, a retire hook run twice, or a refused stop.

## Upgrade

- **`@awebai/oats` declares the Node it needs: 22.5.0 or later.** Check
  `node --version` on each host before upgrading. On an older Node, `npm
  install -g @awebai/oats` now warns `EBADENGINE` (and refuses where npm's
  `engine-strict` is set): install Node 22, whose current releases are all
  past 22.5, then install OATS. Hosts on Node 22.5 or later change nothing.

- **Either order of the Desktop and the CLI works.**
  [Upgrading](../upgrading.md) installs the Desktop first, and a host that
  installed the CLI first is fine too: the 0.69.15 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`, as the 0.69.14 Desktop does.
- **Package pins** are 0.69.14's: oats.framework 1.23.0, oats.okf 5.8.0 and
  oats.aweb 1.37.0.

- **Upgrade hosts to keep tasks off their command line.** A spawn routed
  with `--server` keeps its task off every command line only on a host that
  runs this release. An older host still gets the task as an argument, and
  the spawn's answer warns that it was readable in both machines' process
  lists.

- **Tighten a record root that an earlier version wrote.** The turn-record
  store now creates its files and directories for their owner alone (see
  Fixed below), and it never changes the permissions of what already exists:
  journals, objects and index databases written before this release keep the
  mode they were created with, `0644` and `0755` under the usual umask. On a
  host with more than one user, run once, for each record root (the `--root`
  given to capture, else `$TURN_RECORD_ROOT`, else `~/.turn-record`):

  ```sh
  chmod -R go-rwx ~/.turn-record
  ```

  A process that reads a record root as another user, or through a group,
  can no longer read what the store creates from this release on; run it as
  the root's owner.

- **A capture lock or a stream lock written by an earlier version is still
  judged as that version judges it.** Its record names neither a boot nor a
  process start: the capture lock (`<record root>/.capture.lock`) is
  reclaimed only when it names this host and its pid is gone, and a stream
  lock (`streams/<id>/.lock`) by its pid on this host, or by its age when it
  names another. One left on a volume by a container that ran an earlier
  version can therefore still stop capture for that root after the upgrade:
  the pass names the lock and the command that removes it. Locks this
  version writes do not need that.

- **A record root is written from one machine at a time.** A record root
  must not be shared by two machines. A lock taken on
  another machine was taken in another boot, so it is reclaimed at once
  though its holder may be running there. Earlier versions never reclaimed
  another host's capture lock, and reclaimed another host's stream lock only
  after 30 s. A record root that two machines write at once (a home on NFS)
  is no longer serialized between them
  ([turn record: Durability and concurrency](../../packages/record/README.md#durability-and-concurrency)).

- **After upgrading, release any schedule slot left without its record.**
  An earlier OATS killed while it took a job's slot could leave the
  directory `<deployment>/.agents/schedules/locks/<id>/` with no
  `owner.json` in it. This OATS never writes into it or removes it for
  you: `oats doctor` lists it as a `schedule-slot-unreadable` problem, the
  tick reports that job invalid, and the slot counts against
  `maxConcurrent`. Check `oats schedule show <id>`; once its last run is
  not running, run `oats schedule reconcile <id> --clear` to release it
  ([Schedules](../schedules.md#files)).

## Added

- **`oats host run`: the kernel's periodic work in one foreground process,
  for a host without a timer** (oats-project/oats#1789). Every `oats` command is
  short-lived, and the resume sweep and the schedule tick were started by a
  client or by a host timer. A container has neither, so nothing there
  resumes sessions after a restart, runs schedules, or stops the agents in
  order when the container stops. The command is what an operator, or the
  entrypoint of an image, runs for that; the agent image in
  `container/agent/` does not run it yet
  ([container.md](../container.md#the-kernels-periodic-work)).
  - `oats host run [--stop-grace <seconds>] [--plan] [--json]` runs the
    resume sweep once, then `oats schedule tick --host` at second 0 of every
    minute for the registered scopes, and lists the instances each minute so
    that the next start's sweep knows what ran. A minute whose tick still
    runs is skipped, and a missed minute is never replayed. With no scope
    registered it ticks nothing and says so.
  - On SIGTERM or SIGINT it stops ticking, waits for a tick that runs, then
    stops every running instance side by side: SIGTERM to the harness, a
    wait of `--stop-grace` seconds (default 20), never escalated. It exits
    0. The next start's sweep resumes those instances.
  - It refuses to start, before any effect, inside an instance session
    (`E_USAGE`), while the host timer is active (`E_HOST_RUN_TIMER_ACTIVE`),
    and while another `oats host run` holds this machine's lock
    (`E_HOST_RUN_BUSY`). Unit files that are installed and not active are a
    warning. The lock names its boot, so a lock left by a killed container
    is taken over by the next run.
  - `--plan` says what a run would refuse, the scopes it would tick and what
    its sweep would do, and changes nothing.
  - New contracts
    ([desktop-cli-api.md](../desktop-cli-api.md#the-host-run-oats-host-run)):
    the command and its flags; its answer, `{schemaVersion, plan, signal,
    warnings, sweep, ticks, stopped}`, and its plan, `{schemaVersion, plan,
    refusals, warnings, scopes, sweep}`; `E_HOST_RUN_BUSY` with
    `details.lock` and `details.found`; `E_HOST_RUN_TIMER_ACTIVE` with
    `details.unit`; `E_HOST_RUN_FAILED` for any other failure of the run.
- **`oats schedule host install --register-only`** records the deployment in
  the host schedule registry, with any caps given, and installs no timer
  (oats-project/oats#1789). It asks neither launchd nor systemd for
  anything, so it works in a container, where plain `host install` fails
  after registering. It does not go with `--print`. With `--server` it is
  sent only to a host that advertises the new feature
  `schedule-host-register-only` (and `schedule`); any other is refused here
  with `E_REMOTE_INCOMPATIBLE` before anything is sent, since a host that
  does not know the option ignores it and installs a timer. New contracts:
  the flag; its answer, which is `host install`'s; and the feature
  `schedule-host-register-only` in the probe
  ([schedules.md](../schedules.md#without-a-host-timer)).
- **A session that OATS stopped with the host is resumed**
  (oats-project/oats#1789). A stop by `oats host run` writes the home's stop
  record with `"resume": true` and `"reason": "host-stop"`, before the
  harness is signalled. Such a home reads `sessionEnd: "lost"`, whatever
  status its harness ended with; `sessionEnd` has no new value, and every
  other stop still reads `stopped`. `oats status` says `lost (stopped with
  the host)` under a local row. A new contract: `resume` and `reason` in
  `.oats-stop.json`
  ([execution-targets.md](../execution-targets.md#how-a-sessions-end-is-read)).

- **`oats spawn <soul> --task-file -` reads the task from standard input**
  (feature `spawn-task-stdin`). A terminal on standard input is refused
  (`E_BAD_ARGS`).

- **`oats doctor` lists a schedule slot whose record cannot be read** as a
  `schedule-slot-unreadable` problem, `{code, severity, scope, id, message,
  remedy}`, naming the deployment, the job and the remedy
  ([Schedules](../schedules.md#what-a-run-reports)).
- **`oats doctor` lists a schedule slot whose schedule is gone** as a
  `schedule-slot-orphaned` problem of the same shape, naming the run and the
  instance its record names, and, for a workspace schedule, the time of the
  saved snapshot that says it is gone. A workspace schedule absent from the
  snapshot that cannot be shown gone is listed with the step that applies.

## Changed

- **A spawn through a server is bound to the server's preview and a key.**
  `oats spawn <soul> --server <id>` asks the server for its preview, then
  spawns with that decision and a key made for the request
  (`--expect-decision`, `--idempotency-key`): one more call to the server
  per spawn. Its `--json` answer is the server's keyed answer, with
  `decision`, `replayed` and `wake` beside the fields it had. A name another
  spawn takes between the two calls is `E_DECISION_STALE` and nothing is
  created: run the spawn again. `--suggest-name` is given to the preview,
  and the spawn carries the name it chose. A spawn that brings
  `--expect-decision` or `--idempotency-key` travels as given
  ([Run there](../servers.md#run-there)).
- **A server that does not advertise `spawn-preview-2`, `spawn-apply-2` and
  `spawn-idempotency-2` gets the spawn in one call, as given,** and the
  answer carries a warning that a dropped link cannot be retried safely
  there.

- **The kernel's package declares `engines.node: >=22.5.0`.** It declared no
  floor, while CI runs Node 22 and the turn record the kernel ships reads its
  index through `node:sqlite`, which Node has from 22.5. The floor is the one
  `@awebai/turn-record` already declared. `npm run validate` holds the root
  package to a declared floor, the lock to the same one, and every package
  under `packages/` to no lower one.
  [First team](../first-team.md#0-prerequisites) states the floor.

- **An owner whose liveness can't be judged is never reclaimed.** The
  remote cache write lock (`<cache>/.locks/<repo>.lock`) and the turn
  record's capture and stream locks read a lock's owner through one
  function, which answers "unknown" for a pid whose existence cannot be
  checked (`kill` answers neither `ESRCH` nor `EPERM`) and for a record
  whose pid is no process ID (zero, a negative number, one above the
  range). The cache write lock reclaimed a lock without a boot or a start
  on such a failed check, and one of another boot whatever its pid; it
  waits for both and refuses with `E_REMOTE_UNREADABLE` (`reason:
  "cache"`), as for a live holder. For a pid that is no process ID the
  refusal says that the lock names none and is safe to remove once no oats
  process is running, and its details carry no `holderPid`
  ([Implementation](../implementation.md)).

- **A home whose record does not say which retire hooks to run is refused by
  `oats retire`, where it was removed with a warning.** A record that names
  no repository and does not show that no capability has a retire hook (the
  stub a spawn leaves when it is killed before its record) is refused with
  `E_UNIDENTIFIED_INSTANCE_HOME` before anything is stopped, run or removed,
  unless a usable cleanup marker is beside it. Clean up by hand what the
  home's capabilities registered, then `oats retire <instance> --force`
  removes it, running no hook
  ([capabilities.md](../capabilities.md#manifest)).
- **`spawnInProgress: true` on a status row, and `E_LIFECYCLE_BUSY` from a
  retire, also cover a spawn that is running its spawn hooks**, when a
  capability with a spawn hook has a retire hook. Before, only a spawn
  running its `worktree` hooks read that way.

- **A retire's lifecycle claim records the retire hooks that ended.** The
  claim file of a home (`<instances>/.oats-retirement/claims/<name>.lock`)
  gains two fields while a retire holds it: `retireHooks`, a list of
  `{capability, meta?}` for each retire hook that ended, with the `meta` it
  answered, and `retireHooksFor`, the `createdAt` of the home they ran for.
  This is an addition to the claim's format. An earlier OATS that takes
  such a claim over ignores the fields and runs every retire hook, as it
  always did. This OATS, taking over a claim without them, runs every
  retire hook too. Nothing is written into the home
  ([One retire at a time](../desktop-cli-api.md#retire-hooks-in-claim)).

- The [team agent image](../container.md) pins OATS 0.69.14, adding file-backed launch environment and the operator's harness token route; amd64 and live-lab acceptance remain separate evidence.

## Fixed

- **A schedule's job slot is never left without its record.** The slot was
  made as an empty directory and its record written into it after, and
  released by removing the record before the directory, so a tick killed
  between the two steps left a slot without its record. The record is now
  written first, in a directory beside the slots, and that directory is
  renamed to the slot; a release renames the slot out before removing it
  ([Schedules](../schedules.md#files)).
- **A slot whose record cannot be read stops only its job.** Such a slot
  (an earlier OATS's, a hand edit, a disk fault) made every tick of its
  deployment fail with `job lock custody is unreadable`, so none of the
  deployment's jobs ran, and `oats schedule reconcile` answered `nothing to
  reconcile`. The tick now reports only that job `invalid` and runs the
  others; `oats schedule reconcile <id>` answers the remedy, and
  `reconcile <id> --clear` releases the slot once you have checked
  ([Schedules](../schedules.md#files)).
- **A slot left by a schedule that is gone can be released.** A local
  schedule removed by hand, or a workspace schedule removed upstream, could
  leave its slot, which every tick counted against `maxConcurrent` and no
  command could release: `oats schedule reconcile` and `remove --force`
  answered `E_SCHEDULE_UNKNOWN`. The slot still counts until it is released,
  since its run may still be going; `oats schedule reconcile <id>` now
  answers what it found, and `reconcile <id> --clear` releases it once you
  have checked, with the job's retained attempt and state; a gone
  schedule's retained state with no slot is cleared the same way. A workspace
  schedule is gone only when the saved snapshot shows it: run `oats
  automations refresh` first if the snapshot is stale. One that is disabled,
  untrusted or placed elsewhere is refused as before, and `oats doctor`
  names the step that acts for its unreadable slot: remove it by hand once
  `oats status` shows no run of it here, never a `reconcile --clear` that
  refuses it ([Schedules](../schedules.md#files)).

- **A spawn whose link dropped while the server spawned can be run again
  onto the one instance.** The failure is `E_SSH`, its message ends with the fix, and
  `--json` carries `error.details: {decision, idempotencyKey, fix}`. The same
  spawn with `--expect-decision <decision.revision> --idempotency-key
  <idempotencyKey>` answers the instance the first attempt created
  (`replayed: true`) and saves its route
  ([ssh failures](../desktop-cli-api.md#ssh-failures-e_ssh)).
- **A replayed keyed spawn answers `attach`,** as the first apply did.

- **The turn-record store creates transcripts private to their owner.** The
  store created journals, objects, quarantined copies and its index
  databases with the process's default permissions, so on a shared host
  other users could read agents' conversations. It now creates files with
  mode `0600` and directories with mode `0700`:
  [Store layout](../../packages/record/docs/turn-record-sot.md#store-layout)
  has the rule.

- **A capture lock or a stream lock whose holder is gone no longer stops
  capture when the container is created again.** Both locks of the turn
  record named their holder by pid and hostname. On a volume that outlives
  its container, a lock left by a stopped container named a hostname the
  next container does not have, so the capture lock was never reclaimed and
  every pass skipped, and a pid that the next run had given to another
  process, so the lock read as held. Both records also name the boot the
  lock was taken in and the holder's process start (`bootId`,
  `processStart`), as the kernel's claims do, and are judged by the same
  code: a lock taken in another boot (a container run counts as one), or
  whose pid is gone or runs with another start, is reclaimed at once,
  whatever host it names. The capture lock's registered worker and its
  reclaim guard are judged the same way. A holder that is still running is
  never taken over, and a pass that finds one says that it skipped, naming
  it ([turn record: Durability and concurrency](../../packages/record/README.md#durability-and-concurrency),
  #1812).
- **The standalone `turn-record` package judges its locks as an OATS
  install does.** The process start token, the boot id and the rule for a
  record of another boot are one dependency-free module of the package,
  `packages/record/lib/process-identity.mjs`, which the kernel imports
  ([Implementation](../implementation.md)).

- **A spawn killed inside its spawn hooks no longer leaves a registration
  that nothing can release.** `oats spawn` ran its spawn hooks (a
  capability's may register an identity with an external service and take a
  seat) and wrote the home's record only later. A spawn killed in between
  (SIGKILL, a container stop, a dropped connection) left a home whose record
  named neither a repository nor its capabilities; `oats retire` then ran no
  retire hook, removed the home and the keys in it, and exited 0 with a
  warning.
  - The spawn now writes its in-progress marker
    (`.oats-rollback-incomplete.json`) before its first spawn hook, in every
    work mode, when a capability with a spawn hook has a retire hook: the
    repository, the capabilities with their hooks, the soul, and the record's
    `workspace`, `teams` and `defaultTeam`. It writes it again with the spawn
    hooks' receipt once they have answered, and removes it when the final
    record is written.
  - `oats retire` of the home such a spawn leaves runs the retire hooks,
    with the environment a retire of a whole home gives them, and then
    removes the home. A retire hook that runs after a spawn hook that never
    answered gets an empty `OATS_META`.

- **A self-retire whose completion was killed says what to run, and a
  reboot no longer hides that it was killed.** `oats retire <instance>
  --self` schedules the retire in a detached completion and leaves a pending
  marker beside the home. When that completion was killed before it
  finished (a `SIGKILL`, a container that stopped), `oats session start`
  answered `<instance> is being retired`, which was not true and named no
  way out. It now answers `E_INSTANCE_RETIRING` with `<instance> is owed a
  retire (its retire was interrupted): finish it with` and the `oats retire`
  command, which takes the retire over and completes it. The marker also
  records the boot its completion runs in (`completionBoot`): after a
  reboot or a container restart, a marker whose pid and start had both come
  again read as a retire still running, and `oats retire` was refused
  `E_LIFECYCLE_BUSY` for a completion that no longer existed. Such a marker
  now names a completion that is gone. A marker written by an earlier OATS
  names no boot and is judged by its process alone, as before
  ([a completion that was killed](../souls-and-instances.md#self-retire-interrupted)).

- **A spawn whose caller went away no longer ends as a failure, or with a
  home that has no record.** When the reader of `oats spawn` closed stdout
  or stderr while it ran (an ssh session that ended), the spawn completed
  and then ended with an unhandled `EPIPE` and exit status 1, as if it had
  failed. It now ends with the spawn's own status, `0`, as `oats worktree
  add` does; the answer nobody read is the home's record, and a spawn
  repeated with the same `--expect-decision` and `--idempotency-key`
  answers it again. A SIGINT, SIGTERM or SIGHUP that arrived while the
  capabilities were copied into the new home ended the process there and
  left a home with no `instance.json`, which only `oats retire --force`
  removed. The signal is now held until the copy ends: the home is removed
  and the spawn answers `E_INTERRUPTED` (`details: {signal, hooks: []}`),
  exit 128 + the signal number, as it does while its `worktree` hooks run
  ([a caller that goes away](../desktop-cli-api.md#spawn-caller-gone)).

- **A stop is not refused by a self-retire whose completion is gone.** A
  scheduled self-retire whose detached completion was killed, or that
  failed after its hooks started, leaves its pending marker, and every stop
  of that home answered `E_INSTANCE_RETIRING`: `oats instance stop
  --apply`, a retire's stop of a recorded child, and the stop `oats host
  run` makes of every running home on SIGTERM, which reported a failed stop
  on each container stop. The marker now holds the home against a stop only
  while the completion it names is not gone. Once it has ended, runs with
  another start, or belongs to another boot, the stop plan shows `retiring:
  false` for that target and the session is stopped; the marker stays, and
  the home is still owed its retire (`oats retire <instance>`). A
  completion that lives, and a marker that names none, refuse a stop as
  before
  ([a completion that was killed](../souls-and-instances.md#self-retire-interrupted)).

- **A retire, a session start, a session restart and a stop apply whose
  caller went away no longer end as failures.** When the reader of `oats
  retire`, `oats session start`, `oats session restart` or `oats instance
  stop --apply` closed stdout or stderr before the answer was written (an
  ssh session that ended, a Desktop that quit), the act completed under
  the home's lifecycle claim and the process could then end with an
  unhandled `EPIPE` and exit status 1: a retire did, and so did a start
  that started the OATS tmux server, which writes a line on stderr while it
  acts. They now end with the act's own status, as `oats spawn` and `oats
  worktree add` do, and what could not be printed is dropped
  ([a caller that goes away](../desktop-cli-api.md#spawn-caller-gone)).

- **A retire that takes over from a killed one no longer runs again the
  retire hooks that one had finished.** A retire, or the detached
  completion of a self-retire, that was killed after some of its retire
  hooks had returned (a `SIGKILL`, a container that stopped) left nothing
  that said so, and the next `oats retire` of the home ran every hook a
  second time. The next retire now reads
  the finished hooks from the claim the killed one left, skips them, and
  judges the cleanup and writes its `retired` row with what they answered.
  A hook that had not ended when the retire was killed is run again. The
  retry of a quarantined home, and the retries a self-retire's completion
  makes of a cleanup its hooks left incomplete, run every hook again, as
  before
  ([One retire at a time](../desktop-cli-api.md#retire-hooks-in-claim)).

- **A checkout OATS makes runs no filter driver the repository's
  configuration defines.** The `git worktree add` of a spawn into a worktree,
  and the `git worktree add` and `git switch` of `oats worktree add`, ran the
  `filter.<name>.smudge` or `.process` command the clone's configuration
  names for a file carrying the `filter` attribute, as whoever spawned. Each
  is preceded by one read of that configuration, and every driver it defines
  is overridden to no command, as for a retire's status: such a file is
  written as its committed bytes
  ([a checkout runs no filter driver](../souls-and-instances.md#checkout-filter-drivers)).
  - A driver the operator's global or system configuration defines runs as
    before: Git LFS set up with `git lfs install` checks its files out. With
    `git lfs install --local` alone, a tree OATS checks out holds the
    pointer files: run `git lfs install`, or `git lfs pull` in the tree.
  - A driver whose name cannot be passed on Git's command line (it holds `=`
    or is not UTF-8) refuses the checkout. The spawn's refusal is
    `E_WORK_INSPECTION_FAILED`, as before, raised before
    `git worktree add` and no longer at the baseline's status, with the
    message `could not make the instance worktree: git worktree add was not
    run in <clone>: …`; `oats worktree add` answers `E_GIT_FAILED`.
- **No Git command OATS runs on a work tree's files or index runs the file
  monitor the repository's configuration names.** The same three commands,
  the fetch of `oats worktree add`, the reads of `oats worktree remove` (its
  status, the clean check inside `git worktree remove`, the comparison of an
  unregistered tree's surviving files) and the check `oats package
  add|remove` makes that `oats-workspace.yaml` is tracked ran the
  `core.fsmonitor` command of the repository's configuration when they read
  the index of the tree. They run with `core.fsmonitor=false`, as a retire
  and `oats instance git` do
  ([no file monitor](../souls-and-instances.md#no-file-monitor)). The clone's Git
  hooks (`post-checkout` among them) still run at these checkouts.
- **A driver of the operator's that has no `process` command runs where the
  repository's configuration names the same driver.** This reaches every
  command that takes these overrides: a retire and `oats worktree remove` as
  well as a checkout. Each overrides that driver with the operator's values.
  They also set its `process` to nothing, which made Git skip the operator's
  `clean` and `smudge` commands. `process` is left alone when neither
  configuration defines it. When the repository defines it and the operator
  does not, neither side's command runs.

- **A spawn through a server that runs this release keeps the task off every
  command line.**
  `oats spawn <soul> --server <id>` with `--task` or `--task-file` put the
  whole task text in the remote command, so it was in the arguments of the
  local `ssh` process and of the server's `oats` for as long as each ran,
  readable by every user of either machine in the process list. The text
  goes on the ssh session's standard input, to the server's preview and to
  its spawn, and the remote command carries `--task-file -`
  ([a routed spawn's task](../servers.md#a-routed-spawns-task)). A task
  file over Linux's limit for one argument (128 KiB) is sent like any
  other.
- **A spawn with a task through a server that does not advertise
  `spawn-task-stdin` says where the task was readable.** Such a server gets
  the task as an argument, as before, and the answer's warnings gain one
  line: `remote oats <version> at <host> does not advertise
  spawn-task-stdin, so the task was passed as an argument, visible in this
  machine's process list (the ssh command) and the host's while the spawn
  runs; upgrade the host`.

  hooks: one must be safe to run when its spawn hook did not finish and when
  it has run before.
