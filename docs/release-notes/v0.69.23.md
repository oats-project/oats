# OATS 0.69.23

An agent can keep facts in its person's view and ask them questions with options, on its board
(`oats instance board`), and oats.core teaches agents to use it. The Desktop reads an agent's own mail, received and
sent, in a read-only sheet that never marks anything read, through the messaging layer's new `messaging:mail`
operation (oats.aweb 1.46.0). The sidebar draws lines between related work again, and the kernel's same-work flag becomes the related-work flag, which also binds a sibling (the old spellings stay as aliases). The team image's supervisor runs
one generic optional child, and the bb image moves to its own repository. The catalog pins oats.framework 1.27.0,
oats.aweb 1.46.0 and oats.okf 6.3.0.

## Upgrade

- **Either order of the Desktop and the CLI works** from a Desktop newer than
  0.69.17 ([Either order works](../upgrading.md#either-order-works)).
- **Package pins:** oats.framework 1.27.0 (from 1.26.0), oats.aweb 1.46.0
  (from 1.45.0) and oats.okf 6.3.0 (from 6.2.0). `oats sync` takes them.
  Respawn instances, or move a stopped one with `oats instance upgrade`, to
  take the new modules: the board teaching (oats.core 2.15.0) and the mail
  read (oats.aweb 1.46.0) reach an agent only through its module copies.
  Until then the Desktop's mail sheet shows `E_OPERATION_UNKNOWN` for that
  agent.
- **The mail read needs aw 1.36.53 or later**; below it, it answers
  `E_AW_TOO_OLD` (oats.aweb's aw floor is unchanged otherwise).
- **If you tried the experimental bb image of 0.69.22** (`container/agent-bb`
  with `container/agent/compose.agent.bb.yaml`): rebuild your team image
  from this release's `container/agent`, since the 0.69.22 supervisor does
  not know `AGENT_CHILD`; build the bb image from
  [oats-project/oats-bb](https://github.com/oats-project/oats-bb) on that
  team image; replace `compose.agent.bb.yaml` in your Compose commands by
  that repository's fragment, which sets `AGENT_CHILD: "bb"`; and set no
  `AGENT_BB`. A container that still sets `AGENT_BB` does not start.
- **The same-work flag is now the related-work flag; the old spellings
  still work.** `oats spawn … --same-work` and `oats instance same-work …`
  are deprecated aliases of `oats spawn … --related-work` and `oats instance
  related-work <instance> on|off`, with the same binding. Each use prints one
  line on stderr (`--same-work is renamed: use --related-work`, `oats
  instance same-work is renamed: use oats instance related-work`); `--json`
  output is unchanged. Instances flagged before the upgrade keep their flag.
  Move skills and scripts to `--related-work` once every host they run
  against is on this release; the aliases stay until their removal is
  decided, with its own release-notes entry.

## Added

- **An agent's mail in the Desktop.** Alt+M (⌥⌘M on macOS), the palette's **Agent: mail** or **Mail** in Details opens the agent's own mail, received and sent, newest first, in a read-only sheet from the right. Each message shows who it is from or to, its subject and its body as plain text attributed to its sender, and whether it is encrypted, not read by the agent yet, high priority or from an unverified sender. **r** reads it again, **Older mail** reads further back, and Esc closes it ([An agent's mail](../desktop.md#an-agents-mail)).

  Reading it never acknowledges or marks anything read: the Desktop runs only the messaging layer's `messaging:mail` operation, and only when you open the sheet or ask it to read again. Nothing else on the screen shows an agent's mail. It needs an agent whose messaging layer has the operation; an older one says to upgrade it (`oats instance upgrade`) or start a new agent of its soul.

- **The agent's board** (feature `instance-board`, `boardApi: 1`). An agent
  keeps facts in its person's view and asks them questions, from its own
  session:
  - `oats instance board set <key> --label <text> --value <text> [--unit
    <text>] [--link <https-url>]` and `oats instance board unset <key>`. At
    most 12 facts. The kernel keeps each fact's last 20 values. Facts last as
    long as the home.
  - `oats instance board ask <question> --option <text> --option <text>
    [--option <text>]… [--id <id>] [--context-file <f>]` and `oats instance
    board ask --clear <id>`. Each question has 2 to 4 options. At most 9 are
    open, with ids `q1`, `q2`… (never reused) unless `--id` names one. A
    question belongs to the session it was asked in.
  - While a question is open, the kernel holds a needs-input claim of
    producer `oats.board`, reason `attention`, with the oldest question as its
    message. The waiting dot and the waiting row show it as they show any
    claim. It holds no scheduled wake.
  - `board` on `oats status --json` and `oats server roster --json` instance
    rows: the facts and the open questions, at most 8 KiB per row
    (`E_BOARD_FULL` refuses a write past it), or `null` with no board.
    `oats inspect --home <h> --board` adds each fact's history and each
    question's context.
  - The board is the home's `.oats-board.json`. It is kernel-owned: a
    capability can't declare it, and a retire counts it as no work.
  - The kernel routes no answer. A client types the person's answer in the
    agent's terminal as `<id>: <text>`.

  See [The agent's board](../desktop-cli-api.md#the-agents-board-oats-instance-board).

## Changed

- **Related work, with a parent or a sibling** (feature
  `instance-related-work`; `instance-same-work` is still advertised beside
  it). The flag binds an instance's recorded parent, as before, and now also
  its recorded sibling when it has no parent. A top-level instance's sibling
  can carry it, so clients can draw a line between two siblings. A sibling
  binding names the sibling the home records: a sibling of a top-level R
  binds R, and a sibling of R's sibling S binds S. `--related-work`, and
  `oats instance related-work <instance> on`, on an instance that records
  neither a parent nor a sibling are refused with `E_BAD_ARGS`, naming why,
  and nothing is spawned or written. The flag reads off after a relink that
  changes the relation (a parent or a sibling retired), until `on` binds it
  again.
- `oats status --json` rows carry `relatedWork: true`, and `sameWork: true`
  beside it when the flag is bound to the parent (never for a sibling). The
  verb answers `{"instance", "relatedWork", "sameWork"}`. The home file is
  `.oats-related-work.json`, `{"relatedWorkApi": 1, "parent" | "sibling":
  "<instance>", "at": "<ISO time>"}`. An existing `.oats-same-work.json`
  still reads as a parent binding while the new file is absent; the first
  write of the new file removes it, and `off` removes both. Both
  `.oats-related-work` and `.oats-same-work` are kernel-owned home names: a
  capability cannot declare either.
- **`--server`.** The roster and `oats status --server --json` relay
  `relatedWork: true`, and `sameWork: true` beside it for a parent binding.
  A host on an older OATS, which advertises only `instance-same-work`, is
  sent the old spellings for an instance bound to its parent, and its rows'
  `sameWork: true` reach this machine with `relatedWork: true` beside it. A
  sibling binding is refused there with `E_REMOTE_INCOMPATIBLE`, naming the
  host and the feature it lacks; it is never dropped. See
  [Related work](../desktop-cli-api.md#related-work-oats-instance-related-work).
- **The team image's supervisor runs one generic optional child, and knows
  no product.** A derived image declares the child in
  `/etc/agent-child.json` (its command, literal and file-read environment,
  readiness URL, loopback ports, version check and stop budget, in a closed
  grammar), and the deployment switches it on from outside the image with
  one fixed Compose entry, `AGENT_CHILD: "<name>"`. Without the switch the
  supervisor reads no file and runs as on the base image. With it, the
  supervisor refuses the start, before any child, on a missing or malformed
  declaration, a declaration that is not root's own regular file, a name
  that differs from the switch, or a command that resolves under a writable
  mount. The child's order, start timeout, restart backoff and process
  group are fixed in the base image; its stop budget is capped at eight
  seconds, so the ordered stop fits the 50-second grace whatever an image
  declares. A file-read variable must hold its value on one line: a file
  with whitespace inside its value refuses the start, and the value reaches
  only the child. Acceptance with `AGENT_CHILD=<name>` exported reads the
  declaration from the running container and checks the file, the declared
  listeners, that nothing but sshd listens beyond loopback, and the declared
  version. Every agent in the container can reach the child's loopback
  ports. See [An optional child](../container.md#an-optional-child).

- **OATS pins oats.aweb 1.46.0** (from 1.45.0). It adds the view operation `messaging:mail`: an instance's own mail, read without acknowledging anything, which the Desktop's mail sheet reads (`mailApi: 1`, [Mail](../desktop-cli-api.md#mail-mailapi-1)). Floors are unchanged: OATS >=0.68.0, aw >=1.36.33, tested aw 1.36.58. The mail read alone needs aw >=1.36.53 and answers `E_AW_TOO_OLD` below it. Running instances keep the module they were spawned with: respawn them, or move a stopped one with `oats instance upgrade`, to take 1.46.0. Until then, their mail sheet shows `E_OPERATION_UNKNOWN`.

- **Desktop: the sidebar draws its lines again, for related work only.** Where an instance's host
  reports related work, the sidebar draws the lines it drew before its redesign, closed or open,
  and the command palette draws the same lines by the same rule
  ([the sidebar's instance tree](../desktop.md#the-sidebars-instance-tree)).
  - **A solid line** joins a parent to a child whose work is related to its parent's. Any other
    child keeps its indent with no line.
  - **A dotted line** joins the dots of two top-level instances of one group when the one linked
    as a sibling of the other reports related work. A top-level instance whose work isn't related
    breaks the dotted line, and the order of the rows doesn't change.
  - **No flag, no line, on every host.** On an older OATS (with `instance-same-work` only), a
    child's line follows `--same-work` and siblings get none. An OATS with neither feature reports
    no related work, so its instances get no line (before, the command palette drew every line
    for it).
  - Both lines hold 3:1 contrast on every row fill, in every theme. A screen reader hears
    "related work" after "under <parent>", and after "sibling of <name>" at both ends of a joined
    pair, in place of the words it heard for a child's flag before.

- **oats.framework 1.27.0** (`oats.core` 2.15.0, `oats.knowledge-theory` 1.1.2,
  `oats.setup` 2.16.1). `oats.core`'s inject and `/oats-operate` teach the
  agent's board where the kernel lists `instance-board`, with `attention` as
  the fallback (#2002). The `knowledge-capability-authoring` skill, its copied references
  and the `knowledge-theory-expert` soul teach judgment and proposal at the
  working instance's own checkpoints, with a reviewer accepting every
  proposal. An independent harvester is an option a capability may choose
  (#2009). `oats.setup`'s onboarding and package-pins skills name oats.okf
  v6.3.0 in their examples. Guidance text only: no floor moves, and nothing
  changes for a deployment beyond `oats sync` taking the new tag.

- **`oats.core` teaches the agent's board.** Its inject and `/oats-operate`
  say that, where `oats version --json` lists `instance-board`, an agent
  asks a decision between 2 and 4 options on its board (`oats instance board
  ask`, with the summary, context, next step and links in `--context-file`,
  and an option for each choice saying what it does). The answer arrives typed as `<id>: <text>`, and the
  agent closes the question with `oats instance board ask --clear <id>` once
  it has read it. The agent keeps only what its person must keep in view as
  board facts (`oats instance board set`). On an OATS without the board (no
  `instance-board` feature), it uses `oats instance attention`;
  after `E_EVENTS_FAILED` it runs the same board command again.
  See [The agent's board](../desktop-cli-api.md#the-agents-board-oats-instance-board).

- **The official catalog pins oats.okf 6.3.0** (from 6.2.0), and OATS's own
  workspace takes it. Knowledge proposals are lighter (oats-project/oats-okf#164):
  `oats okf propose` refuses only what protects against real harm (secrets and
  personal data leaving the host, a base that would be invalid, forged
  provenance, unsafe files, the soul's consent, credentials, one attempt per
  proposal). What the knowledge maintainer judges at review anyway (a claim
  outside the proposer's nodes, a missing subject, a broken link, an unfilled
  `proposal.md`) becomes a `W_*` warning, listed under `## Check warnings` in
  the PR body, which the maintainer resolves before merging. `--slug` and
  `--digest` are optional: `--plan`, then `--apply` (it prints the outgoing
  diff and stops), then `--apply` again publishes exactly what it printed.
  Every 6.2 invocation still works with the same result. **What a deployment
  must change:** nothing; the floor stays OATS >=0.69.2. Running instances
  keep the module they were spawned with: respawn them, or move a stopped one
  with `oats instance upgrade`, to take 6.3.0. The generated mirror under
  `mirrors/oats-okf*` is finalized from the v6.3.0 tag
  ([oats.okf's CHANGELOG](https://github.com/oats-project/oats-okf/blob/v6.3.0/CHANGELOG.md)).

## Fixed

- **Getting started pushes straight to a free plan's private repository.**
  On a private repository whose plan has no rulesets, GitHub answers the
  `oats-getting-started` skill's rules read with a 403 "Upgrade to GitHub
  Pro". Step 7 read that failure as a guarded branch and opened a pull
  request the person then had to merge. It now counts that 403 as no rules,
  as `oats-workspace-config`'s check already does. The skill still opens a
  pull request when others can push, when the branch is protected, when any
  other read fails, or when the push is refused.
- **Getting started's default workspace name is the repository's.** When a
  project has both a repository and a folder of different names, step 1 now
  proposes the repository's name, and the folder's only when there's no
  repository.

## Removed

- **`AGENT_BB`, `container/agent-bb`, `container/agent/compose.agent.bb.yaml`
  and the bb relay have left this repository.** They shipped in 0.69.22 as
  experimental, with no compatibility promise in that release's docs and
  notes, and are removed without an alias. The bb image, its Compose
  fragment, the relay and their operator docs now live in
  [oats-project/oats-bb](https://github.com/oats-project/oats-bb), where the
  image declares bb as its optional child and its fragment sets
  `AGENT_CHILD`. A container that still sets `AGENT_BB`, to any value, is
  refused at start with a line that names `AGENT_CHILD`, and acceptance
  refuses it too.

## Documentation

- **The knowledge-capability authors' guide teaches proposals, not a
  harvester.** The reference model's judgment step is now the working
  instance's own, at its knowledge checkpoints, with a reviewer accepting every
  proposal: [judgment and proposal](../knowledge-reference/proposal.md)
  replaces the harvester page, and the model, reader/capture, provider-mapping,
  acceptance and package-craft pages follow it. An independent harvester stays
  an [option](../knowledge-reference/adoption.md#an-option-an-independent-harvester)
  a capability may choose, with the obligations it then carries. The
  `oats.knowledge-theory` skill `knowledge-capability-authoring`, its copied
  references and the `knowledge-theory-expert` soul change with it; they ship
  with the next `oats.framework` release.

- **A view operation may carry one structured field.** Beside its `documents`, a view's result may hold one field named after its operation and versioned by its own `<name>Api`. The kernel validates `documents` only and relays the result unchanged, locally and through `--server`, so a client can rely on the field reaching it as the provider wrote it ([desktop-cli-api.md](../desktop-cli-api.md#oats-operation-run)).
- **`messaging:mail`, `mailApi: 1`: an agent's own mail, read without acknowledging it.** The messaging layer's answer is described once for every messaging provider: received and sent mail, newest first across the agent's identities, with bounded bodies and answers, paging, partial long conversations, per-identity errors and how older sides answer ([desktop-cli-api.md](../desktop-cli-api.md#mail-mailapi-1)). oats.aweb is its first provider. No kernel change: an older kernel relays it the same way.
