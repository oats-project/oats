# OATS 0.69.16

0.69.16 moves OATS onto oats.okf 6: there is no knowledge harvester any more,
and an instance proposes what it learned itself, as a pull request the
knowledge maintainer reviews (`oats okf propose`). The official catalog pins
oats.okf 6.0.1, oats.aweb 1.39.0 and oats.framework 1.24.0, and OATS's own
texts, souls and template copy follow. The team agent image now runs
`oats host run`.

## Upgrade

- **Either order of the Desktop and the CLI works.**
  [Upgrading](../upgrading.md) installs the Desktop first, and a host that
  installed the CLI first is fine too: the 0.69.16 Desktop accepts OATS CLIs
  `>=0.26.0 <0.70.0`, as the 0.69.15 Desktop does.
- **Package pins:** oats.okf 6.0.1 (from 5.8.0), oats.aweb 1.39.0 (from
  1.37.0) and oats.framework 1.24.0 (from 1.23.0). A deployment that pins
  them takes the steps below; one that keeps its own pins changes nothing
  until it moves them.

- **A deployment that takes oats.okf 6.0.1 does these by hand**, from its
  deployment directory (oats.okf's
  [Upgrading to 6.0](https://github.com/oats-project/oats-okf/blob/v6.0.1/README.md#upgrading-to-60)
  has each step's commands; [knowledge.md](../knowledge.md#pin-and-select-the-package)
  the summary):
  1. Delete the harvester's launch preference, if any:
     `oats soul launch remove oats.okf/knowledge-harvester --plan`, then
     without `--plan`.
  2. Delete every `--provider oats.okf harvest=…` spawn flag from the
     scripts and briefs that spawn instances. Remove a leftover host
     `harvest` key with `oats okf setup --remove-legacy-settings --soul
     <soul>` (`--plan` first).
  3. Add the `proposal-review` trigger beside `harvest-review`: an existing
     `harvest-review` watches only the 5.x label `okf-harvest`, so it never
     reviews a 6.0 proposal. For a workspace file, copy it under the template
     `oats.okf:proposal-review` and the id `okf-proposal-review`, keeping its
     `set:`, `runsOn` and `owner`. On its review host, if `oats-local.yaml`
     lists named `automations: trust:` entries, add
     `- <member>/okf-proposal-review` beside the old one, then check that
     `oats trigger show <member>/okf-proposal-review --json` answers
     `runsHere: true`. For a local trigger, read its values with `oats
     trigger show <id> --json` and repeat them as `--set` values on `oats
     trigger add --from oats.okf:proposal-review`. Remove `harvest-review`
     (and its trust line) once no 5.x harvester can open an `okf-harvest`
     PR.
  4. Protect every Git base's accepted branch (pull requests only, merged by
     the knowledge maintainer's account), and give each proposing host's
     account branch-create access on the knowledge repository, never
     accepted-branch push; optionally set `screen-terms-file`
     ([Settings](../knowledge.md#settings)).
  5. Retire the harvesters `oats status` still lists, once they have handed
     over. A retired source's claims are proposed with the operator form,
     `oats okf propose --home <retirement recovery directory> --soul <soul>`
     (`--plan`, `--check`, `--apply`).
- **OATS's own workspace** adds `oats-triggers/okf-proposal-review.yaml`
  beside `okf-harvest-review.yaml`. On the host it names, add its trust line
  as in step 3 unless that host trusts `"*"`.

- **oats.aweb 1.39.0 tests aw 1.36.56** (from 1.36.53). The floor stays
  aw 1.36.33. `aw-newer-than-tested` now warns only above 1.36.56, and the
  pin it names is `npm i -g @awebai/aw@1.36.56`. Install that version on
  each host where readiness asks for it.
- **pi homes: remove or filter `@awebai/claude-skills` in the launch's pi
  folder.** From oats.aweb 1.38.0, home readiness warns
  `pi-skills-package-loaded` when that pi folder lists
  `npm:@awebai/claude-skills` without `"skills": []`. Remove the entry, or
  filter it. With @awebai/pi 0.5.0 or later installed there,
  `pi-extension-skills-loaded` no longer asks for the skills filter.
- **Bringing your own team** (`oats aweb setup --create <label> --namespace
  <domain>`) needs aw 1.36.53 or later, and refuses an older aw before it
  creates anything.

- **Rebuild the [team agent image](../container.md) and recreate its
  container.** The image pins OATS 0.69.15 and its entrypoint runs
  `oats host run`; an existing container keeps the old entrypoint, the
  10-second stop timeout and no healthcheck until it is made again from the
  new image and `container/agent/compose.agent.yaml` (`docker compose ... up
  -d`). `container/agent/accept.sh` refuses a container whose stop timeout
  is not 45 seconds or whose healthcheck is not the service file's.
- **A platform that does not read the Compose file** gives the container a
  stop timeout of 45 seconds itself: `oats host run` gives each harness 20
  seconds to end, and Docker's default of 10 kills the agents before they
  are stopped in order.
- **Register the deployment for schedules once**, after `server connect`:
  `oats schedule host install --register-only --server team-agent`. The
  operator's OATS must be 0.69.15 or later for the option.

## Changed

- **The official catalog pins oats.okf 6.0.1** (from 5.8.0, crossing 6.0.0),
  and OATS's own workspace takes it. 6.0 removes the knowledge harvester: an
  instance proposes its knowledge by pull request at its checkpoints (`oats
  okf propose`), and the knowledge maintainer reviews it. `oats.okf-harvest`
  and `oats.okf/knowledge-harvester` stay as refusing stubs until 7.0. It
  also reads a bridged knowledge base by subject (`okf.json` version 2, and
  the `subjects`, `subject`, `claims` and `verdicts` verbs); a base that is
  not bridged, and a version-1 soul, are served as before. The generated
  mirror under `mirrors/oats-okf*` is finalized from the v6.0.1 tag
  ([oats.okf's CHANGELOG](https://github.com/oats-project/oats-
  okf/blob/v6.0.1/CHANGELOG.md)).

- **OATS's texts follow oats.okf 6: an instance proposes its own knowledge.**
  The docs, the souls and the `oats.framework` skills no longer name a
  harvester to launch, wait for or retire: at each knowledge checkpoint an
  instance with a duty to propose runs `oats okf propose` itself, and the
  knowledge maintainer's review gates the pull request
  ([knowledge.md](../knowledge.md#the-flow),
  [schedules.md](../schedules.md#knowledge-proposal-review)). A finished
  instance's done line is one of "done, proposed: <PR URLs>", "done, nothing
  to propose: <reason>" or "done, no duty to propose"; "done, proposal
  pending: <slug and why>" means it is not finished yet.

- **`oats.framework` 1.24.0 carries OATS's texts for oats.okf 6 and the pi
  folder steps for @awebai/pi 0.5.0.**
  - `oats.setup` 2.15.0:
    - `/oats-onboarding`, `/oats-automations` and `/oats-agent-permissions`
      describe oats.okf 6.0.1: an instance proposes its own knowledge with
      `oats okf propose`, the `oats.okf:proposal-review` trigger reviews it,
      and there is no harvester to set up.
    - `/oats-host-delivery`'s pi step asks for the skills filter only below
      @awebai/pi 0.5.0, and keeps @awebai/claude-skills out of OATS pi
      folders.
  - `oats.coordination-setup` 1.0.1's `/coordination-best-practices` says
    knowledge is proposed at checkpoints, not harvested.

  The commands these name come from oats.okf 6, which the catalog pins. None
  needs a newer OATS than each capability already admits.

- **OATS's copy of the engineering template moves to template-v3.0.2**, which
  makes the same change in the coordination skills and injects.

- **The official catalog pins oats.aweb 1.39.0** (from 1.37.0, crossing
  1.38.0), and OATS's own workspace takes it. It brings:
  - from 1.38.0, the pi skills-filter change above;
  - from 1.39.0, a bring-your-own-team create that runs to the end
    (registers the team, publishes and verifies its team-server record, and
    resumes when re-run); a public `aw-compat.json` stating the aw floor and
    the tested aw; and owner-only draft files for mail and chat bodies
    instead of fixed `/tmp` paths.

  `mirrors/oats-aweb` and `mirrors/oats-aweb-tasks` are copied from the
  v1.39.0 tag
  ([oats.aweb's CHANGELOG](https://github.com/awebai/oats-aweb/blob/v1.39.0/CHANGELOG.md)).

- **The team agent image runs the kernel's periodic work.** Its entrypoint
  starts sshd in the background and ends in `exec oats host run`, so that
  command is tini's direct child, the process the runtime's SIGTERM reaches
  and the container waits for. At start it resumes the sessions lost when
  the container last stopped, then runs the schedule tick each minute for
  the registered deployments; on `docker stop` it stops the agents in order
  and the next start resumes them
  ([container.md](../container.md#the-kernels-periodic-work)).
  - The image pins OATS 0.69.15, the first release with `oats host run`.
  - The Compose service sets `stop_grace_period: 45s`.
  - The Compose service has a healthcheck that opens sshd's port,
    `127.0.0.1:2222`, every 30 seconds. `oats host run` does not supervise
    sshd, and Docker does not restart an unhealthy container: when
    `docker inspect --format '{{.State.Health.Status}}'` reads `unhealthy`,
    `docker restart` the container.
  - The acceptance script requires the 45-second stop timeout and that
    healthcheck in the container's inspect evidence.

## Documentation

- **The pi skills filter is for @awebai/pi below 0.5.0, and @awebai/claude-skills stays out of OATS pi folders.**
  - **Why:** @awebai/pi 0.5.0 bundles no skills. They now ship on their own in @awebai/claude-skills, which pi would load in every session that uses the folder.
  - **`/oats-host-delivery`** (`oats.framework`): the pi step of channel delivery makes the extension's entry `{"source": "npm:@awebai/pi", "skills": []}` only below 0.5.0.
  - **The getting-started onboarding:** it still sets the filter whatever the version, because it's harmless on 0.5.0.
  - Both now say never to install @awebai/claude-skills in a pi folder that OATS homes use, because a home gets its skills from its capabilities. This matches oats.aweb 1.38.0, whose readiness warns `pi-extension-skills-loaded` only below 0.5.0 and adds `pi-skills-package-loaded`.
