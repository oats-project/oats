# OATS 0.70.1

Unreleased

A preview on a session provider now asks the provider's own readiness check,
so it no longer reads clean for a launch the provider then refuses. A
schedule's save asks the same, with the job's own `yolo`. tmux homes and their
previews are unchanged.

## Upgrade

- **The Desktop and the CLI** can be upgraded in either order.
- **A scheduled or triggered spawn on a provider that launches only in full
  mode (bb's)** needs `yolo: true` in its definition, or a launch
  configuration that sets it. A job without it is now refused when saved, where
  it used to fail at each run.

## Changed

- **A spawn job on a session provider is checked by the provider when it is
  saved.** A spawn's preview now asks a session provider's `check` with the
  launch that is planned, and `oats schedule add`, `update` and `test` ask
  that preview with the job's own launch selection, its `yolo` included
  ([spawn](../schedules.md#kinds)). On a provider that launches only in full
  mode:
  - a job with `yolo: true` is saved and launches, as one whose launch
    configuration sets yolo does (a build with the preview's new check and
    without this change refused the job's own `yolo: true` on `add` and
    `update`, and `oats schedule test` said its soul did not resolve: the
    schedule's preview did not carry it);
  - a job with no `yolo` is refused when saved (`E_SCHEDULE_INVALID`,
    `details.code: "E_BACKEND_SANDBOXED_MODE"`), and `oats schedule test`
    reports it, where it used to fail only at its run. One the
    save did not ask the provider about (its soul was already spawned in
    the deployment, or the provider comes from a member module, which a
    preview does not ask) fails at each run, `launch-failed` with `errorCode:
    "E_BACKEND_SANDBOXED_MODE"`, and leaves no home.

## Fixed

- **A preview on a session provider no longer reads clean for a launch the
  provider will refuse.** `oats spawn --preview` of a spawn on a session
  provider read complete, with no problem and no warning, and the spawn was
  then refused by the provider's readiness check and undone (with a provider
  that launches only in full mode and no full-mode choice:
  `E_BACKEND_SANDBOXED_MODE`). A preview now asks the provider's `check` with
  the launch that is planned, as the spawn does before any hook runs
  ([spawn preview](../desktop-cli-api.md), [check](../capabilities.md#check-optional)):
  - a launch the provider would refuse fails the preview with the spawn's own
    code and creates nothing; a provider that cannot be asked is
    `E_BACKEND_NOT_READY`; one that outlasts the preview's budget leaves
    `preflight.status: "timeout"`;
  - `oats launch-config preview --home` of a provider home asks it too, and
    shows a refusal as a failed `backend` item, with `ok: false`;
  - a provider in a member module, which runs only from a spawned home, is
    not asked: the preview says so in `warnings`.

  For a provider's author: `check` may now be handed a home that does not
  exist yet (a spawn's preview hands its planned path). It must only read,
  and treat an absent home as absent.

## Documentation

- **Schedules and triggers on a session provider**
  ([Kinds](../schedules.md#kinds), [Triggers](../schedules.md#triggers)): a
  scheduled or triggered spawn on a provider that launches only in full mode
  needs `yolo: true` in its definition, or a launch configuration that sets
  it; a wake is the input of a provider home's session, and never starts a
  stopped provider home. Tests now cover a wake, a scheduled spawn and a
  triggered spawn on a session provider.
