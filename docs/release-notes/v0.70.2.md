# OATS 0.70.2

Unreleased

A pi agent waiting on a dialog now reads as needing input, and a scheduled
wake holds until it is answered. The Desktop's Schedules form edits a schedule
on a session provider. The catalog pins oats.aweb 1.48.0 and oats.framework
1.29.0.

## Upgrade

- **The Desktop and the CLI** can be upgraded in either order.
- **The pi bridge** (`@awebai/oats-pi` 0.70.2) reaches each pi folder with
  `oats update`; until then a pi agent's dialog sets no claim.
- **OATS pins oats.aweb 1.48.0, which needs OATS 0.70.0 or later.** Upgrade
  the CLI to 0.70.0 or later before `oats sync` takes the pin: an older kernel
  refuses the package. Running instances keep the module they were spawned
  with: respawn them, or move a stopped one with `oats instance upgrade`, to
  take 1.48.0.

## Added

- **A pi agent's question raises needs-input, in every pi home.** Nothing set a
  claim when a pi instance waited on a dialog, so it read as running while it
  waited for a person, and a scheduled wake's Enter answered the dialog. The pi
  bridge (`@awebai/oats-pi`) now holds a waiting claim of producer `oats.pi`,
  reason `question`, for as long as a dialog an extension opened is open (a
  question tool's `select`, `confirm`, `input`, `editor` or custom screen),
  with the dialog's title as its message. `oats status`, `oats session inspect`
  and the Desktop show the instance as needing input, with the question, and a
  scheduled wake holds until the dialog is answered
  ([A held wake](../schedules.md#a-held-wake)). The claim clears when the
  dialog closes and when the session ends with it open. It reaches every pi
  home, a pi in a tmux pane and one a session provider runs in RPC mode alike,
  on pi 0.84.4 and later, and needs the bridge updated in each pi folder
  ([upgrading](../upgrading.md)). No key or event is new: the claim is the one
  a failed turn already uses, and an open dialog is shown over a failed turn
  ([A pi dialog](../capabilities.md#oatscore-needs-input)).
  - **The bridge clears only its own claim.** It records a mark while its claim
    stands, `<home>/.pi/oats-pi-claim.json`, naming the pi process that set it,
    and tells its claim by that mark, never by the claim's reason. A second pi
    in the home (a nested one, a subagent's session) no longer clears a live
    pi's claim at its first run, and never replaces its question. No other
    producer's claim is touched.
  - **A pi that died with its dialog open.** Its question is cleared when the
    home's next pi starts. With no pi to start it stays and holds the home's
    scheduled wakes, on a session provider until it is cleared: `oats instance
    waiting clear --producer oats.pi --home <home>`.
  - **What it does not cover.** A pi home's `wakeHold` still reads `unknown`:
    the kernel can't see whether the bridge is loaded, and a screen of pi's own
    (its project trust prompt, a picker a person opened) has no claim.

- **Desktop: the Schedules form edits a schedule that launches on a session
  provider.** A new-agent schedule's **Session backend** now offers tmux and
  each session provider the chosen soul's capabilities supply (bb, where the
  soul has it), and **Edit** opens a schedule stored on one instead of sending
  you to the CLI; a save keeps the backend
  ([Scheduling agents and wake messages](../desktop.md#scheduling-agents-and-wake-messages)).
  - bb launches only in full mode: choosing it sets permissions to YOLO and
    the form says why. A schedule saved without it (with the CLI, say) is
    marked **Refused at each run** (`yolo: false`) or **Needs YOLO** (no
    `yolo`: refused unless its launch configuration sets it) in the list and
    on its page.
  - A wake to an agent on a session provider is edited as any wake. The form
    says it is sent as the session's input and never starts a stopped agent
    there.
  - An Edit that is still reading the soul's session backends is dropped by
    anything else that happens to the list meanwhile (a switch, a run, a
    Delete, a refresh, another workspace), so a late answer never brings back
    a form holding the old definition.

## Changed

- **OATS pins oats.aweb 1.48.0** (from 1.47.0). The package's requirements
  follow the session backend: the channel packages (`aweb-channel`,
  `@awebai/pi`) are required of `tmux` launches only, and a session provider's
  launch requires an installed `aweb-channel` to be 1.7.9 or later, and an
  installed `@awebai/pi` 0.3.10 or later, so no older package opens its own mail stream beside
  the wake broker's. A retire removes a provider home's broker registration
  when either record names a session provider. Homes on tmux behave as before.

- **oats.framework 1.29.0** (`oats.core` 2.16.1, `oats.knowledge-theory`
  1.1.4).
  - `oats.core`'s `/oats-operate` says a pi home's extension dialogs raise
    needs-input, and that the claim holds a scheduled wake while one is open,
    from `@awebai/oats-pi` 0.70.2 (#2071). A pi home's `wakeHold` still reads
    `unknown`: a screen of pi's own has no claim.
  - `oats.knowledge-theory`'s capability-authoring reference shows the
    `oats.framework` v1.28.0 pin in its example (it showed v1.27.0).
  - The catalog pins oats.framework 1.29.0.
  - Guidance text only. Nothing changes for a deployment beyond `oats sync`
    taking the new tag; existing homes take the new skills through
    `oats instance upgrade` or a new spawn.
