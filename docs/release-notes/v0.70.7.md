# OATS 0.70.7

Unreleased

A patch release of package pins and guidance: oats.aweb 1.49.1 (human
attribution, and retire fixes) and oats.framework 1.30.0 (how to adopt a
minting root, documented for when it opens). No kernel or Desktop code
changes.

## Upgrade

- **The Desktop and the CLI** can be upgraded in either order: their code
  is unchanged. Upgrade the CLI before `oats sync`, so that the catalog's new pins
  resolve.
- **OATS pins oats.aweb 1.49.1** (from 1.48.0). Its floor stays OATS 0.70.0.
  Running instances keep the module they were spawned with: respawn them, or
  move a stopped one with `oats instance upgrade`, to take 1.49.1. A private
  deployment publishes its namespace authority in DNS; for a registry at a
  non-public address, set the registry origin in `oats-local.yaml`
  (`settings.oats.aweb.registry`). If DNS also names a non-default registry,
  the two must agree.

## Changed

- **OATS pins oats.aweb 1.49.1** (from 1.48.0; 1.49.0 and its patch):
  - support for aw 1.36.59: username setup resumes the signup aw kept after an
    unknown outcome, and aw retires a local member itself where this machine
    holds its team's controller key;
  - human attribution: the provider reads who stands behind a root or an
    identity (`aw who`) and shows it. Adopting a root on a hosted team is not
    open yet;
  - a home the kernel keeps after a retire no longer holds a usable aweb key;
  - `aw who` gets the configured registry;
  - retire keeps a home where a configured root reaches into it through a
    link, and on macOS paths that spell a home, the deployment or a root in
    another case are compared by their on-disk spelling (1.49.1).

- **oats.framework 1.30.0** (`oats.setup` 2.17.0, `oats.knowledge-theory`
  1.1.5).
  - `oats.setup`'s `/oats-teams` explains how to adopt a minting root (human
    attribution, optional; #2082), and that the adopting person's namespace
    must verify (human IDs contract r3 §2; #2110). It names what it needs: aw
    1.36.59 or later on every host that uses the root, and oats.aweb 1.49.0
    or later. Adopting a root on a hosted team is not open yet.
    `/oats-onboarding` lists the adoption as an optional card.
  - `oats.knowledge-theory`'s capability-authoring reference shows the
    current `oats.framework` pin in its example.
  - Guidance text only. Nothing changes for a deployment beyond `oats sync`
    taking the new tag; existing homes take the new skills through
    `oats instance upgrade` or a new spawn.

## Documentation

- **Adopting a minting root: optional human attribution, documented for when it
  opens** ([oats-project/oats#2059](https://github.com/oats-project/oats/pull/2059)).
  OATS's adoption of hosted roots stays closed until the human IDs contract's
  gates G2 (aweb's Cloud journey run) and G1's adopted evidence are met, although
  aweb Cloud 0.8.81 already offers the dashboard steps. When it opens, with aw
  1.36.59 and oats.aweb [1.49.0](https://github.com/awebai/oats-aweb/tree/v1.49.0),
  the release with human attribution, a person can adopt one of a deployment's
  minting roots, and the instances it mints from then on trace to them.
  [Adopting a minting root](../integrations.md#adopting-a-minting-root-oatsaweb-optional)
  gives which roots, what it needs in aweb Cloud and who can adopt, the agent's
  two `aw id parent` commands and the person's dashboard acts, the check, and
  its limits: one adoption per root, and no un-adopt (a team admin, or an owner
  or admin of the owning organisation in the team, removes the root's
  membership from their own terminal with a dashboard setup key). Attribution
  grants no access. oats.setup's `/oats-teams` has it as an act card, and
  `/oats-onboarding` routes to it. A deployment that adopts nothing works as
  before.
